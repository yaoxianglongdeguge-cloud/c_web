### 1.1 瓶颈：单个收发线程

`c=200`（51 884 rps）时逐线程 CPU：

```
tid=收发线程   69.9% 核     ← 天花板在这里
tid=业务线程1   9.8% 核
tid=业务线程2   8.6% 核
```

配合"服务端 CPU/请求 ≈ 18~19µs"：**单核理论上限 ≈ 53~74k rps**，实测峰值正好落在这个区间。
也就是说：**2 个 vCPU 里还有约 0.9 个核没被利用**——因为收发（accept/read/epoll/发送/定时器）全跑在一个线程里，而 2 个业务线程几乎闲着。

### 1.2 两点必须说明（否则数字会被误读）

1. **"QPS"强依赖客户端模型**：上表是"一个连接发一个请求、等响应再发下一个"（wrk 默认）。
   若客户端**一次发一批**（pipelining），单连接一次发 500 个可在 **5.1ms** 内收完 500 个响应（≈9.7 万响应/秒/连接）——那是"批量排空速率"，**不是每请求延迟**（那些响应是分批挤出来的，最后那个等了 5.1ms）。
2. **业务越重 QPS 越低**：`POST`（解析+回显，CPU/req 79µs）只有 1.4 万，静态文件（CPU/req 31µs）3.5 万。**6.2 万是"最理想业务"（13 字节文本响应）的上限。**

### 1.3 过载时的表现：先 503，再卡死

| 并发 | QPS | 非2xx（503）比例 | 压后服务器状态 |
|---|---|---|---|
| ≤300 | 5.3~6.2 万 | **0%** | 健康 ✅ |
| 400 | 1.5~5.2 万 | **1%~18%** | 可能**卡死**（不可恢复）❌ |
| 600 | 1.3~2.4 万 | 20%~30% | 严重过载（503 为主） |
| 800 | 3.3 万 | **25%** | 严重过载 |

→ 说明 **c≥400 时系统已经进入"过载保护"状态**（内存池非扩容 ⇒ 分配不到就回 503），而**死锁就发生在这个过载最深处**。

## 2. 死锁成因（本报告重点）

### 2.1 现象：进程活着，但完全不可用、不会自恢复

三次独立复现（每次都是新进程）：

| # | 触发方式 | 压测结果 | 压完探测 `/hello` |
|---|---|---|---|
| 1 | `wrk -t2 -c400 -d10s`（连压 3 轮） | 第 3 轮 **rps=0** | 无响应 |
| 2 | 两个 wrk（各 `-t1 -c200`，合计 400 连接） | 2 656 rps | 无响应 |
| 3 | `wrk -t2 -c400 -d10s`（干净新进程） | 15 089 rps、726 个 503 | **探测超时（000）** |

三次卡死现场完全同一个形态：

```
三个线程状态:   收发线程 S/futex_do_wait   业务线程1 S/futex_do_wait   业务线程2 S/futex_do_wait
                （全部阻塞在信号量/互斥锁上，不是在 epoll 也不在 read）
监听队列:       LISTEN  101/100      ← accept 队列塞满，新连接直接被丢（客户端 connect 超时）
连接状态:       CLOSE-WAIT 414~601 个 ← 客户端都关了，服务器没来得及 close
进程本身:       存活、RSS ~4MB、不崩溃 —— 但永远不恢复
```

### 2.2 关键证据：两个"阻塞式 sem_wait"在过载时**都被真实撞到**

我在副本（`/tmp/dlA`）里加了探针：打印 4 个队列的实时深度，并在"即将阻塞"时报警。压 c=400/600 时同一轮里就出现了：

```
[BLOCK] 业务线程→收发线程：Thing_queue 已满 100/100 ⇒ 业务线程即将阻塞在 sem_wait     （出现 5 次，探针上限）
[BLOCK] 收发线程→业务线程：worker memory_queue 已满 100/100 ⇒ 收发线程即将阻塞在 sem_wait （出现 5 次）
```

队列深度采样（每 200ms 一条）：

```
[MON 398] taskQ=0/100   收发.ThingQ=75/100   业务1.memQ=0/100  业务2.memQ=0/100
[MON 399] taskQ=52/100  收发.ThingQ=100/100  业务1.memQ=1/100  业务2.memQ=0/100   ← 收发队列满
[MON 401] taskQ=69/100  收发.ThingQ=100/100  业务1.memQ=9/100  业务2.memQ=0/100
[MON 403] taskQ=0/100   收发.ThingQ=0/100    业务1.memQ=43/100 业务2.memQ=2/100
```

→ **`Thing_queue` 在过载时反复打到 100/100（满）**；两个 `memory_queue` 也出现过 100/100。
两个队列容量都是 **100**：
`Threads/ReceiverThread.c:34` `ReceiverQueueInit(&((*w)->Thing_queue),100)`
`Threads/WorkerThread.c:81`  `WorkerQueueInit(&((*profes)->memory_queue),100)`

### 2.3 机制：两条"阻塞式投递"方向相反 ⇒ 循环等待（经典死锁）

```
        业务线程 ──投递响应──► 收发线程的 Thing_queue ──┐
             ▲                                          │ 满(100/100) ⇒ 业务线程阻塞在这里
             │                                          ▼
       业务线程的 memory_queue ◄──归还响应内存── 收发线程
             ▲                                          │
             └── 满(100/100) ⇒ 收发线程阻塞在这里 ◄──────┘
```

**两条阻塞路径（都是无超时的 `sem_wait`）：**

| 方向 | 函数 | 阻塞点 | 谁调用它 |
|---|---|---|---|
| 业务 → 收发 | `ReceiverQueuePush` | `Queue/ReceiverQueue/ReceiverQueue.c:29` `sem_wait(&(sq->sem_thing_queue_notfull))` | `Threads/WorkerThread.c:186`（错误响应）、`:194`（正常响应） |
| 收发 → 业务 | `WorkerQueuePush` | `Queue/WorkerQueue/WorkerQueue.c:30` `sem_wait(&(sq->queue_notfull))` | `ResponseSend/ResponseSendMain.c:38`、`:66`（发送/回收包）；`FdConnectResource/SendPointerPool/SendPointerPool.c:54`（经 `FdClose`→`SendPointerPoolDestory`→`SendPointerPoolClear`） |

**死锁怎么形成（时序）**：
1. 收发线程一时供不上（要 read+完整性检查+哈希+投递，还有发送和定时器都在它身上）⇒ 它排空 `Thing_queue` 变慢 ⇒ **`Thing_queue` 被打满**；
2. 此时两个业务线程各自想投递下一个响应 ⇒ 卡在 `ReceiverQueuePush` 的 `sem_wait`（等收发线程腾出位置）；
3. 与此同时连接在关闭/发完，收发线程走到 `FdClose` → `SendPointerPoolClear` → 要**归还响应内存给某个业务线程的 `memory_queue`**；如果那个队列也满（业务线程正忙/正卡着，没来得及 `CleanMemoryQueue`）⇒ 收发线程卡在 `WorkerQueuePush` 的 `sem_wait`；
4. **这时：收发线程等业务线程腾 memQ，业务线程等收发线程腾 Thing_queue —— 没人再排空任何队列，永远互等。**

### 2.4 为什么"永不恢复"（这点比死锁本身更要命）

- 这两处用的是**无超时**的 `sem_wait`（不是 `sem_timedwait`）⇒ 一旦进去就出不来；
- 唯一能"做超时关闭/清理"的定时器 `TimerOvertime(...)` 就跑在**收发线程自己的循环里**（`Threads/ReceiverThread.c:97`）⇒ 收发线程一卡，定时器也停了，**连 60s 空闲超时都不会触发**；
- 没有任何第三方线程能打破这个等待 ⇒ 进程只能靠外部 kill 重启。

### 2.5 为什么是"间歇性"、而且只在 c≥400 出现

- 需要两个条件**同时**成立：`Thing_queue` 满 **且** 某个业务线程的 `memory_queue` 也满（收发线程正在走归还内存那条路）。两者都是瞬时峰（探针显示 `Thing_queue` 在 25→75→100 之间抖动），所以是概率事件；
- c≤300 时队列根本不接近满（压后监听队列 = 0、零 503），所以打不到；
- c≥400 时系统已经在"内存池满 ⇒ 大量 503"的过载区，队列长期高水位（探针实测 75~100），**一次坏时序就锁死**；
- 副作用：跨过一次卡死后，后续即使降到 c=200 也可能继续出现 1~3% 的 503（像留下了"半坏"状态）。

> 附带发现（同一次排查里看到的，**与死锁无直接关系**）：`StaterMain/StarterMain.c:65,72` 把 worker 的 `main_t2` 结构体地址作为 `pthread_create` 参数传出去，而它是**栈上局部变量**——当前靠"`StartThread` 永不返回"侥幸成立（`ReveiverThreadMain` 是死循环），一旦以后改动返回时机就会变成悬垂指针。

## 4. 按你的要求：本次**只诊断、不修改**

下面是"如果要修"的方向（**本次一行代码都没动**，仅供你以后决策）：

| 优先级 | 方向 | 说明 |
|---|---|---|
| 1 | **消除"无超时阻塞投递"**：把两处 `sem_wait` 换成 `sem_timedwait`，超时后走降级（丢弃/503/丢弃响应）而不是无限等 | 死锁的两个必要条件同时去掉一半；代价是要决定"超时后怎么处理这个响应/内存" |
| 2 | **打破"方向相反的互相等待"**：让收发线程**不阻塞地**归还内存（例如归还队列满了就本地暂存一小批/或把归还动作交给业务线程自己从共享池取） | 结构性修法，最彻底 |
| 3 | **抬高/多槽化瓶颈资源**：`Thing_queue`、worker 的 `memory_queue` 从 100 提到 1024，`tempPack` 单槽改多槽 | 只是把触发概率降低，不能根治 |
| 4 | **多收发线程 / 把解析搬到业务线程** | 同时解决"单线程 70% 核就是天花板"的 QPS 问题（见第 1.1 节） |

> 建议的验证方式：修完后重复"c=400/600 各 10 轮"并检查 `ss -ltn` 的 Recv-Q 恒为 0、`CLOSE-WAIT` 不堆积、以及零 503/零卡死。
