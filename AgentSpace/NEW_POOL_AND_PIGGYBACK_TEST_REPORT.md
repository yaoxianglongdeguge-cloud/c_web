## 三、按原样运行：第一个请求 SIGSEGV（P0）

启动正常（进程在），发一个 `GET /hello` → 进程立刻消失、无 stderr。valgrind 现场：

```
Use of uninitialised value of size 8
   at MemoryPoolAlloc (MemoryPool.c:84)              ← int h = p->hint;
   by RequestTempPoolAlloc (RequestTempPool.c:47)
   by RequestComeMain (RequestComeMain.c:16)
   by ReveiverThreadMain (ReceiverThread.c:117)
Invalid read of size 4  ... Address 0x28 is not stack'd, malloc'd or (recently) free'd
Process terminating with default action of signal 11 (SIGSEGV)
  Access not within mapped region at address 0x28
```

**根因链**：

1. `MemoryPool.c:59`：`if(perSize <= 0 || (perSize & (perSize-1)) != 0) return 0;`
2. 四处调用都是 `MemoryPoolInit(&p, 2024*1024, 8)`，`2024*1024 = 2072576` **不是 2 的幂** → 直接 `return 0`；
3. 关键：`return 0` 发生在 `(*p) = malloc(...)` **之前**，所以 `*p` 完全没被写；
4. `ReceiverThreadInit` 里 `*w = malloc(sizeof(Receiver_Thread))` 没清零，刚分配的首触页恰好是 0 → `store_area == NULL`；
5. 第一个请求进来 → `MemoryPoolAlloc(NULL, ...)` 读 `p->hint`（偏移 0x28）→ SIGSEGV。

即：**"perSize 非法"这个错误被静默吞掉了，代价是整台服务器在第一个请求就死。**
（`2048*1024` 才是 2MB；四处都要改：`ReceiverThread.c:32,33`、`WorkerThread.c:82,83`。）

## 五、新池在高并发下为什么会"饿死"（探针实证）

我在 `/tmp` 的第三个副本里给 `MemoryPoolAlloc` 失败处加了临时探针（只打印，**没进你仓库**），在 c=200 那轮抓到的现场：

```
[ALLOCFAIL] needSize=6144  perSize=2097152 entryNum=8        ← 接待线程的 store_area
   entry 0 freeSize=260   hadAllocNum=15
   entry 1 freeSize=36    hadAllocNum=30
   entry 2 freeSize=84    hadAllocNum=2
   entry 3 freeSize=156   hadAllocNum=3
   entry 4 freeSize=164   hadAllocNum=2
   entry 5 freeSize=84    hadAllocNum=6
   entry 6 freeSize=196   hadAllocNum=2
   entry 7 freeSize=2096  hadAllocNum=4
```

读法：**8 个子池（共 16MB）全部"满了"（剩余 36~2096 字节，装不下 6148 字节），但在途块只有 64 个（≈几百 KB）**。

机制（`MemoryPool.c` 现有实现）：

1. 每个子池是 **bump 分配**：`allocPtr` 只增不减，`freeSize` 只在分配时减；
2. `MemoryPoolFree` **只做 `hadAllocNum--`**，**不回收空间**；
3. 只有 `hadAllocNum == 0` 时整池复位（`allocPtr=beginPtr; freeSize=totalSize`）；
4. 于是：**一个子池里只要还有"别的连接"的任意一个在途块，它这一整块 2MB 就永远不会被复用**；
5. 高并发下（c≥200，同时在途的请求散布在 8 个子池里），**没有一个子池能等到"计数归零"**，池子只能单向向前推进 → 推进到 8 个子池都被"少量在途块"钉住 → 6KB 的分配失败；
6. 失败点在 `ResponseSendMain.c:46` → `FdClose(..., 503)`；请求副本那层（`RequestComeMain.c:64`）也会 503。

另外 `store_area` 是**两种块大小混放**的：2KB（`RequestTempPool` 的判定块）+ 6KB（`SendPointerPool` 的发送指针块）⇒ bump + 混放 ⇒ 还会额外产生"剩余空间够 2KB 但不够 6KB"的碎片，让饿死来得更早。

**这解释了全部观测**：

- c=50/80：在途块集中在 1~2 个子池，其他子池能归零复用 → 54k QPS 健康；
- c=120：勉强（50k）；
- c=160：开始需要更多子池同时存活 → 吞吐腰斩（2.7 万）；
- c=200/400：8 个子池全被钉住 → 大面积 503，且**流量停了也不恢复**（被钉住的块还在，计数不归零）。

> 顺带：四个池各 16MB（2048KB×8）常驻，RSS 峰值 ~37MB。老池 3.3MB 就能跑完 60 秒压测。

### 5.1 追问："请求都发走了，为什么池子不释放？"—— 累计分配/累计释放 计数证据

给子池加了 `allocs / frees` 两个计数器（仍在 `/tmp` 副本，没进仓库），c=200 跑到分配失败时：

```
[ALLOCFAIL] needSize=2048  perSize=2097152 entryNum=8
   entry 0 freeSize=2040 在途=36 累计分配=   640 累计释放=   604
   entry 1 freeSize= 124 在途=22 累计分配=  1445 累计释放=  1423
   entry 2 freeSize= 156 在途= 1 累计分配= 27587 累计释放= 27586
   entry 3 freeSize=  84 在途=20 累计分配= 85635 累计释放= 85615
   entry 4 freeSize=  76 在途=10 累计分配=  3952 累计释放=  3942
   entry 5 freeSize= 148 在途= 1 累计分配= 22134 累计释放= 22133
   entry 6 freeSize= 100 在途= 1 累计分配=  6693 累计释放=  6692
   entry 7 freeSize= 108 在途= 2 累计分配=110654 累计释放=110652
```

**结论：释放了 11 万次，空间一个字节都没回来。**

- `entry 7`：这个 2MB 子池**累计释放 110 652 次**，`freeSize` 仍只有 **108 字节**；
- `entry 2/5/6`：**在途只有 1 个块（2KB）**，却各自锁住整个 2MB；
- 8 个子池在途合计 93 个块（≈190KB 真实数据），16MB 池子却分不出 2048 字节；
- `entry 0` 更直白：`freeSize=2040`，而这次要 `2048+4=2052`，**差 12 字节**也算失败。

**为什么释放不还空间**（`MemoryPool.c`）：

```c
int MemoryEntryFree(Memory_Entry* e, bool* Cleaned){
    e->hadAllocNum--;                 // ① 只减计数
    if(e->hadAllocNum == 0){          // ② 只有整体归零
        e->allocPtr = e->beginPtr;    //    才把 2MB 一次性复位
        e->freeSize = e->totalSize;
    }
}
```

配合 `MemoryPoolAlloc` 的 **bump 分配**（`allocPtr` 只增不减、`freeSize` 只在分配时减）⇒
**"释放"= 计数 -1；"还空间"= 整个子池同时空掉时的一次性复位。**

而"整个子池同时空掉"在并发下概率≈0：

- 子池要归零，必须那一刻**没有任何一个**属于它的请求在途；
- c=200 时长期有 ~200 个请求在途，摊到 8 个子池 ⇒ 每个子池任意时刻都恒定有几十个块在途（实测 1~36）；
- 所以每块 2MB 都被"少数几个在途块"钉死，`freeSize` 永远停在几十~2000 字节。

老池没有这个问题：它是**按 size class 一条空闲链**，`free` 就是把块挂回链，**下一个请求立刻能用**，不需要"整池归零"。

> 换句话说：不是"没释放"，而是**释放后空间回不到可分配状态**。这也解释了为什么 RSS 平稳（没有泄漏）却全站 503（没有可用空间）——两个现象同时成立。

### 5.2 追问："满了就停止分配、等在途减到零再复位，不就行了？"

**你的推演本身是对的，而且实测确实有自愈的时候**：全新进程跑 c=200，第 1、2 轮各产生 22~23 万个 503，**负载一停就立刻恢复**（`/hello=200`）—— 说明在途块最终全部释放、子池确实归零复位了 ✅。

但它**不可靠**，第 3 轮就永久死了：

```
第1 轮: QPS=30558 非2xx=233096 → 之后 /hello=200   ← 自愈 ✅
第2 轮: QPS=30818 非2xx=222482 → 之后 /hello=200   ← 自愈 ✅
第3 轮: QPS=30220 非2xx=240856 → 之后 /hello=503
空闲 30s 后连打 20 次：200=0 / 503=20              ← 不回
空闲 90s 后：/hello=503  /hello=503                ← 还是不回
LATEFREE 探针（计数已为 0 还在 free）：0 次          ← 不是重复释放/计数减穿
```

失败瞬间的现场（8 个子池，在途合计只有 51 个块）：

```
entry 0 freeSize= 252 在途= 2  allocs=  607  frees=  605
entry 1 freeSize=2032 在途= 4  allocs=11559  frees=11555
entry 2 freeSize= 100 在途=17  allocs=  861  frees=  844
entry 3 freeSize=4148 在途=15  allocs= 3282  frees= 3267
entry 4 freeSize=2120 在途= 4  allocs= 2838  frees= 2834
entry 5 freeSize=4116 在途= 5  allocs= 2535  frees= 2530
entry 6 freeSize=2176 在途= 2  allocs= 1017  frees= 1015
entry 7 freeSize= 132 在途= 2  allocs= 2175  frees= 2173
```

三个让"等减到零"失效的点：

1. **"满了"不等于"停止接收"**。子池只在 `freeSize < 5` 时被标 `freeEntry=false`。像 `entry 3`（还有 4148 字节）**仍然能接 2KB 的请求** ⇒ 它一直在进新块 ⇒ `hadAllocNum` 永远见不到 0。只有被磨到"连最小块都放不下"时才真正关门，而那时它已经积累了来自很多请求的块。
2. **"减到零"要求该子池所有块在同一瞬间都空闲**。c=200 时每个子池稳态有 1~17 个在途块（8 池共 51 个），要 8 个池全部同时归零 ＝ 需要一次**全局静默**。压测期间没有这种静默，只有"停下来的那一刻"才有 —— 第 1、2 轮正是靠这个静默自愈的；但归零机会一旦错过（那一刻恰好还有 1 个块在途），这块 2MB 就再也回不来。
3. **一个块永不复用 = 2MB 永久报废**。第 3 轮之后空闲 90s 仍是 503，而 `LATEFREE=0` 说明**不是**计数被减穿，而是**有块压根没被 free**（高并发路径上某条 `FdClose`/提前 `return` 漏了释放）。老池同样漏一个块只丢 2KB/6KB；新池把它放大成 2MB。8 个池各漏 1 个块＝整站永久 503。

> 因此在"整池归零"模型下，系统必须同时满足两个前提：**(a) 零泄漏，(b) 周期性全局静默**。
> 前者靠人写代码保证、后者靠负载保证，两条都不可控 —— 这就是我建议改成"按块回收（子池内嵌 free list）"的原因：泄漏只丢一个块，也完全不需要全局静默。

### 5.3 备选方案评估：单位位图 + 环形 arena（"缩小分配单位 + 队头回收 + 尾指针回卷"）

> 这是你提的方案，我没有写代码，只做可行性分析。

#### 5.3.1 方案还原（按我的理解）

1. 把 arena 切成固定大小的**小单位**（unit，比如 1KB/4KB），每个单位**独立记 0/1**；
2. 分配 `n` 个单位时一次占满一段，并记下它**覆盖了哪些单位**；
3. 释放时把这些单位计数减一（= 标记为空闲）；
4. 回收时**从 arena 开头**扫，把开头连续空闲的单位"还"回去（head 前进）；
5. 一个大请求在尾部剩余空间放不下时，**尾指针直接回卷到开头**再分配（跨尾不拆分，中间那段空隙先跳过）。

本质上这是"**环形 arena（ring buffer）+ 单位空闲位图 + 队头回收（head 前进）**"，
对比现在的"整池归零"，它把回收条件从"整块 2MB 全空"降到"队头那段连续空闲"，**这是一次实实在在的改进**。

#### 5.3.2 它解决了什么（对比现在的实现）

| 问题 | 现在（整池归零） | 你的方案 |
|---|---|---|
| 需要"全局静默"才能回收 | ✅ 需要 | ❌ 不需要，队头一空就能还 |
| 释放后空间能否立刻复用 | ❌ 要等整池归零 | ✅ 队头扫到就复用 |
| 2KB/6KB 混放导致的"剩 4148 装不下 6148" | ❌ 会失败 | ✅ 单位化后按单位算，不会再有这种 12 字节失败 |
| `free(ptr)` 没有尺寸参数 | 不需要 | ✅ 需要 `unitLen[]`（2B/单位）记录长度，正好补上 |
| "独立计数" | — | ✅ 可以退化成**位图**（单位不重叠，一个单位最多属于一个块，0/1 就够） |
| 元数据成本 | 0 | 位图 1bit + `unitLen` 2B ≈ **0.05%**（16MB/1KB 单位 = 16384 单位 → 2KB+32KB） |
| 分配复杂度 | O(子池数) 扫描 | **O(1)**（可用区 `[tail, head)` 是一段连续区） |

#### 5.3.3 致命点：`从开头回收` = 队头阻塞（head-of-line blocking）

"只能从队头回收"意味着：**队头那个块不释放，它后面所有已释放的空洞都用不上**。
而你们的负载里恰好有**长寿块**：

- `SendPointerPool` 的 6KB 发送指针块：从"该连接第一个响应入队"一直占到"该连接所有在途响应都发完"（`ResponseSendMain.c:177` 的 `ser_nex_send >= ser_fina_send`）；
- 只要客户端**读得慢**（大文件慢速下载、或者迟迟不 ACK），这个块就能活**几秒到几分钟**；
- 它一旦坐在队头 ⇒ 整个 arena（2MB 甚至 16MB）全部停摆 ⇒ **一个慢客户端就能把全站打成 503**（还是一条现成的 DoS 路径）。

更要紧的是**泄漏放大**：队头那个块如果永远不 free，整个 arena 就永久报废。
现在是"1 个钉子废 2MB"，你的方案是"1 个钉子废整个 ring"（如果 ring 开到 16MB 就是 16MB）。

#### 5.3.4 两个改法（都保留你方案的核心，只把"必须从队头"放开）

**A. 位图 + 任意空闲段（first-fit，带 hint）**——把第 4 步从"只还队头"改成"任何连续空闲段都可用"：

- 分配：从 hint 处按 64 位字扫描位图，找一段连续 `n` 个 0（有 hint 时通常几次命中）；
- 释放：只清位，不移动 head（**没有队头阻塞、不要求 FIFO**）；
- 代价：内部碎片 ≤ U-1/块（U=1KB 而块是 2052B 时浪费 ~1KB ≈ 33%，所以要选 U 或按类分池）；扫描最坏 O(单位数)，但 16MB/1KB=16384 位 = 256 个 u64 字，实际配合 hint 是常数级。

**B. 按 size class 分池 + 类内位图/空闲链**（其实等于把老池的"分类空闲链"塞进新池，仍然线程私有、无锁）：

- 你们的申请**本来就全部 1KB 对齐**：分析块 `⌈h/1KB⌉KB`、判定块 2KB、发送指针块 6KB、响应头块 63KB、请求副本 `⌈len/1KB⌉KB`；
- 每类一个 ring/位图 ⇒ 无内部碎片、队头阻塞只影响"这一类"、泄漏只丢一个块（2KB/6KB/63KB）；
- 这是"能自愈"和"能容错"同时成立的唯一组合：**free 立刻可复用 + 泄漏不放大 + 不依赖静默**。

#### 5.3.5 还需要注意的小坑

1. **尾指针回卷丢空隙**：不跨尾拆分时，尾部到 ring 末尾那段（≤ 最大块大小）要等 head 扫过来才能用；512KB 大请求在 2MB ring 里最多浪费 25%。可以允许跨尾拆分（`unitLen` 记两段）来消掉。
2. **`free(ptr)` 定位单位**：必须保证所有块都从单位边界开始（`(ptr-base)/U` 才成立）⇒ 分配尺寸统一向上对齐到 U。
3. **单位不能跨 head**：环形下"可用区"是 `[tail, head)`，大块要能整段放进这个窗口；否则要么回卷、要么失败（要在设计里明确"大块优先从 head 后第一段连续空闲分配"）。
4. **不要把"计数"做成 refcount**：单位不重叠，refcount 恒为 0/1，用位图更快更省。
5. **仍然线程私有**：接待线程的 `store_area` 只被接待线程碰（`httpNeedFree` 也是接待线程分配 + 接待线程 `free`），worker 的池只被自己碰 ⇒ 你的无锁前提仍然成立 ✅。

#### 5.3.6 结论

- **方向对**：把"整池归零"降级成"按单位回收"，就解决了 5.1/5.2 节那两个问题的**根源**；
- **"只从开头回收"是唯一要改的地方**：它会引入队头阻塞（慢客户端就能卡死全场），并把泄漏放大到整个 arena；
- 推荐组合：**按 size class 分池 + 类内位图/空闲链（free 立刻可复用）**；如果一定要保留变长大块，就用"位图 + 任意连续段 first-fit"作为大块专用的那一类；
- 落地前建议先加两个压测项验证容错：① **慢客户端**（读一半就停，占住 6KB 块）看是否影响其他连接；② **故意漏 free 一个块**（注入 bug）看是"少一个块"还是"整站挂"。

#### 5.3.7 追问："干脆每块都做小，允许大请求分布在不同块里"——要分两种情况看

这句话有两个完全不同的含义，代价差一个数量级：

**含义 A：大请求 = 若干小块的"连续段"（run）** —— ✅ 强烈推荐

- 池子里单位是 1KB，`63KB` 头块 = 63 个单位、`512KB` 请求 = 512 个单位，但它们在**地址上连续**；
- 对外行为和"一个大块"完全一样 ⇒ **解析器/打包/发送一行都不用改**；
- 额外好处：2KB 判定块、6KB 发送指针块、63KB 头块混放在同一个池里时，碎片粒度从 **2MB** 降到 **1KB**，5.1 节那种"剩 4148 装不下 6148"基本消失（最坏只浪费 1KB 的尾部）；
- 元数据只需要 `unitLen[]`（2B/单位）告诉 `free(ptr)` 它占了几个单位 ⇒ 顺便补上"新池 free 没有尺寸参数"的问题；
- 你们现在的申请**本来就全部 1KB 对齐**（`⌈h/1KB⌉KB`、2KB、6KB、63KB），所以这套几乎是"天然适配"。

**含义 B：大请求真的拆到地址不相邻的块里（scatter-gather）** —— ⚠️ 代价很大

现在整条链路都**默认"一个请求/响应 = 一段连续内存"**，四处硬约束：

| 位置 | 现在怎么用 | 分散后要改成 |
|---|---|---|
| 解析器 `RequestAnalysisReceive` | `strstr(http_request,"\r\n\r\n")`、`h->ptr` 递增、`Method/Url/Body` 是裸指针 | 流式跨块解析（或用 iovec 拼临时连续视图） |
| `PackTotal`（响应打包） | 把状态行+头+body 拼成一整段连续内存 | 改成分段描述 + `writev` |
| `ResponseSendMain` 发送 | `write(fd, ptr+off, len)`、单段 `off` 做半包续传 | `writev` + 每段偏移（半包逻辑复杂化） |
| 业务 handler | `HApiEcho` 直接拿 `(const char*)r->Body` 用 | handler API 要改成"body 迭代器/分片回调" |

也就是说：**"分散"不是池子自己的事，会把解析、打包、发送、handler 四处一起改**，而且 `writev` 的 `IOV_MAX`（1024）、半包续传的偏移表都是新坑。

**折中（最省事且够用）**：

1. **池内部按 1KB 单位 + 连续 run**（= 含义 A），请求/响应永远是连续内存；
2. **大 body 单独一类**：`> 64KB` 的请求走"大对象池"（例如一个 1MB×N 的专用 arena，或直接 `malloc/free` 一次），
   并把 `WorkerThread.c:257` 的 `allocsize = 4*size` 改成"`size + 元数据`"（4 倍放大正是 512KB 崩掉的直接原因）；
3. **给 body 一个明确上限**（比如 1MB）并返回 **413**，而不是为极少数超大请求承担 scatter-gather 的复杂度。

**量级参考**（单位 1KB）：

| 对象 | 单位数 | 说明 |
|---|---|---|
| 分析块（小请求） | 1 | `⌈h/1KB⌉` |
| 判定块 | 2 | 2KB |
| 发送指针块 | 6 | 6KB |
| 响应头块 | 63 | 63KB |
| 512KB 请求 | 512 | 用大对象类，不进主池 |

位图 + `unitLen` 元数据：16MB / 1KB = 16384 单位 → 位图 2KB + `unitLen` 32KB，**0.05%**。

**结论**：把单位做小 ✅；**"分散到不相邻块" ❌ 不建议**（四处联动改造 + writev 半包地狱）。
用"1KB 单位 + 连续 run + 大 body 单独一类 + 413 上限"，就能拿到你想要的"内存占用小、不会整池报废"的全部好处，且不改协议层代码。

#### 5.3.8 追问："大请求用相邻块（连续 run）+ 头部连续回收，这个组合行不行？"

**可以，而且这个组合本身是自洽的**：大请求 = N 个**地址连续**的单位（对外仍是一片连续内存），回收 = 从队头扫连续空闲位并推进 head。它把回收条件从"整块 2MB 全空"降到"队头连续空闲"，比现在好得多。

但"只从队头"这条**仍然保留两个全局性风险**，而且在你现在的负载下触发得很快：

| 风险 | 触发条件 | 后果（16MB 环） |
|---|---|---|
| **队头阻塞** | 队头恰好是一个长寿块（典型：6KB 发送指针块被**慢客户端**占着，`ResponseSendMain.c:177` 要等 `ser_nex_send >= ser_fina_send`） | head 停住 ⇒ `[tail, head)` 不再增长 ⇒ 环填满 |
| **泄漏放大** | 队头那个块永远不 free（任一 FdClose/错误路径漏掉） | 整个环永久报废（不是 2MB，是全部） |

**为什么说"填满得很快"**（以 c=200、34k QPS 估算）：`store_area` 每请求要 2KB 判定块 + 6KB 发送指针块 ≈ 8KB ⇒ 分配吞吐 ≈ **270MB/s** ⇒ 16MB 的环**约 60ms 就转一圈**。所以只要队头被卡住超过 60ms（一个 10KB/s 的慢速下载就能卡 100 秒），整站会在**1 秒内**变 503。这不是理论风险，是慢客户端直接可打的 DoS。

**关键点：修掉它的成本几乎为零。**
"从队头扫连续空闲位"这件事**本来就要求每个单位有状态位**（否则你无法知道队头是否连续空闲）——也就是说**位图是必须的**。
既然位图已经有了，"只从队头"放宽成"**任意连续 n 个 0 都可以用（带 hint）**"只是把扫描起点从 `head` 换成 `hint`，成本 O(1)~O(单位数/64)，却同时消掉：
- 队头阻塞（慢客户端只占它自己那 6KB，不再影响别人）；
- 泄漏放大（漏一个块只丢 1KB，不再报废整环）；
- 也不需要再维护 head/tail 的环语义（回卷空隙问题一起消失）。

**如果你坚持"只从队头"**，那就必须加一条工程约束来限制爆炸半径：
- **多环分片**（K 个独立环，按空闲量挑选）：一个被钉死的环只损失 1/K 容量，服务仍能跑（代价是要处理"大块必须放进装得下它的环"）；
- 并且必须**保证零漏 free**（配合"分配失败就 503 + 告警"，避免静默恶化）。

**结论**：

| 组合 | 可行 | 建议 |
|---|---|---|
| 相邻连续块 + 只从队头回收 | ✅ 可行 | 需要"多环分片 + 零泄漏"兜底，否则慢客户端/漏块就是整环级故障 |
| 相邻连续块 + 位图任意连续 run（hint） | ✅✅ 最佳 | 位图本来就要 ⇒ 增量成本≈0，HOL 与泄漏放大同时消失 |

#### 5.3.9 四种方案实测对比：glibc malloc / 优化扫描 / 队头+队尾 / 分类空闲链

基准：`/tmp/bm6.c`（不碰仓库）。16MB arena / 1KB 单位 / 2KB(60%)+6KB(40%) / **随机释放（乱序完成）** / 500 万步；
表中的数字 = **一次分配 + 一次释放** 的总耗时（ns）。

| 方案 | 稀疏(200 在途) | 密集(1500) | 满载(3000 ≈73%) | 分配失败数 |
|---|---|---|---|---|
| A. glibc malloc/free | 124.3 ns | 116.3 ns | 76.7 ns | 0 |
| B. 位图 + hint + 游程扫描 | 41.0 ns | 40.7 ns | 41.3 ns | 0（**平均只扫 1.00 个字**） |
| C. 队头+队尾+回卷（你的方案） | 44.6 ns | 40.4 ns | 39.8 ns | **357 / 357 / 405** |
| D. 分类空闲链（参考） | **35.5 ns** | **36.2 ns** | **35.9 ns** | 0 |

**四个结论：**

1. **glibc malloc 最慢**：76~124 ns，是池化的 **2~3 倍**（即使有 tcache）。按 6.8 万次分配/秒算 ≈ **0.5~0.8% 单核**。
2. **"扫描"根本不是瓶颈**：正确的游程扫描平均只扫 **1.00 个字**（一次缓存命中），B 与 C 的速度差在噪声内（41 vs 40 ns）。
   > 更正：本报告早前写的"扫描 142~1050ns、失败 1103 次"是我探针里 `ctz` 用法有 bug 的版本，已作废；以本表为准。
3. **你的方案（C）唯一的代价是失败**：357~405 次 / 500 万次（≈0.01%）拿不到内存 —— 每次就是一个请求 503；而 B/D 是 **0 失败**。
   即：**省掉扫描换来的不是性能，而是可用性下降**（C 并不比 B 快：40.4 vs 40.7 ns）。
4. **分类空闲链（D）最快且免疫碎片**：`alloc`=取链头、`free`=挂回链，各 1~2 条指令，无外部碎片、泄漏只丢一块。

换算成 CPU 占比（6.8 万次分配/秒）：D ≈ **0.24%**、B ≈ 0.28%、A ≈ 0.68% —— 三者都远小于一个收发包的开销，选型应该看**失败率/可预测性**，而不是这几个 ns。

#### 5.3.10 方案三实测（固定页 + 参考起始位置 + 边界可推 + 块可移动）

按 `CWebMemoryPool/whyNeed.md` 里"方案三"的描述实现（`/tmp/bm8.c`，不碰仓库）：
1KB 页、两个尺寸类（2 页=2KB / 6 页=6KB）、每类一个区域 `[b[c], b[c+1])` 和一个游标 `pos[c]`；
撞边界时：① 洞攒够就压缩本类（memmove）② 不够就向邻居借页（邻居整体后移 + **引用边界修正**）。

| 在途上限 | ns/次分配 | 失败 | 压缩次数 | 搬移量 |
|---|---|---|---|---|
| 200（稀疏） | **40.9 ns** | 0 | 1061 | 194 MB |
| 1500（密集） | **63.1 ns** | 0 | 1342 | 2 020 MB |
| 3000（满载 73%） | **117.0 ns** | 0 | 1932 | **6 725 MB** |

与前面几种方案放一起（ns = 一次分配 + 一次释放）：

| 方案 | 稀疏 200 | 密集 1500 | 满载 3000 | 分配失败 |
|---|---|---|---|---|
| glibc malloc/free | 124 | 116 | 77 | 0 |
| 位图 + 游程扫描 | 41 | 41 | 41 | 0 |
| 队头 + 队尾 + 回卷 | 45 | 40 | 40 | **357 / 357 / 405** |
| 分类空闲链 | **36** | **36** | **36** | 0 |
| **方案三（可移动）** | **41** | **63** | **117** | **0** |

**结论**：

1. **稀疏时方案三很快（41 ns，和位图持平）**：因为几乎不触发压缩；
2. **满载时明显变慢（117 ns，比分类链慢 3 倍、比 malloc 还慢）**：压缩是 memmove —— 满载 73% 时搬了 **6.7 GB**，292 ms 内 ≈ 23 GB/s 的内存带宽全部用来搬数据，还会污染缓存；
   而"满载"恰恰是服务器最需要性能的时候；
3. **它确实没有碎片失败（0 次）**，这是它的真正优点（位图/队头方案在满载时会出现零星失败）；
4. **在 c_web 里落地还有一道硬门槛**：方案三要求**所有指向块内的指针都登记为"引用边界"**。
   现在解析器产出的是 `Method / Url / Version / Body` + 头部名/值 + 查询参数等一堆**裸指针**，
   搬移后要么全部修正（每块 6~8 个引用，修正成本 + 漏登记的悬空风险），要么改成"偏移量"访问（等于重构解析层）。
   本基准只登记了 1 个指针 + 1 个内部指针，**真实成本会更高**。

**一句话**：方案三能用、且没有碎片失败，但它的性能代价随负载**反向变化**（越满越慢），
且要求全链路指针登记；除非你需要"零失败 + 可压缩"，否则分类空闲链（36 ns 恒定 + 0 失败）仍是更优选择。

## 五之二、方案说明：分类空闲链（size-class free list）

> 上面 5.3.x 里反复推荐的"分类空闲链"，本质是 **slab / size-class 分配器**：
> 把块按尺寸分成若干类，每类一条**空闲链**，链节点就存在**空闲块自己的前 8 字节**里（零额外元数据）。

```
arena（一开始 malloc 一大块，或按 chunk 向系统要）
 ├── 1KB 类：[块][块][块][块] ...          free1 ──► 空块 ──► 空块 ──► NULL
 ├── 2KB 类：[块][块][块] ...               free2 ──► 空块 ──► NULL
 ├── 6KB 类：[块][块] ...                   free6 ──► 空块 ──► NULL
 └── 63KB 类：[块] ...                      free63 ──► NULL

alloc(n):  从对应类的链头取一个（1~2 条指令）；链空则在本类 chunk 里 bump 一个新块
free(ptr): 把 ptr 前 8 字节写成链头指针，free_list = ptr（1 条 store）
```

**为什么它快、而且不会出现你遇到的病**

| 性质 | 原因 |
|---|---|
| 分配/释放 O(1)、**零扫描** | 取链头 / 压链头，各 1~2 条指令（实测 36 ns/次配对操作） |
| **零外部碎片** | 同类块等大，永远不会有"剩 4148 装不下 6148" |
| **不需要"整池归零"** | free 立刻可复用 ⇒ 不依赖全局静默，也不怕高并发 |
| **泄漏不放大** | 漏 free 只损失那一个块（2KB/6KB/63KB），不会报废 2MB 子池 |
| **线程私有、无锁** | 每类链是某线程独占（和你现在的设计前提一致） |
| **`free(ptr)` 不需要尺寸** | 指针落在哪个类的区间 → 用区间比较/除法即可判定 |

**唯一要设计的点：每类容量**

- 固定切死：某类用完就 503（简单，但要按流量比例配好）；
- 更好：**每类按 chunk 增长**（例如每次向 arena 要 64KB~1MB，切成该类块；某类的 chunk 全空时可整体还给 arena）——
  这样既保持 O(1)、又能按实际流量自适应；上限用一个"总配额"兜底。

**c_web 的 5 个分配点怎么映射**

| 分配点 | 现在的大小 | 归属 |
|---|---|---|
| 判定块 `RequestTempPool` | 2KB | 2KB 类 |
| 发送指针块 `SendPointerPool` | `sizeof(entry)*blocknum`（KB 取整，≈6KB） | 6KB 类 |
| 响应头块 `RspHeaderAlloc` | 63KB | 64KB 类（或 63KB 精确类） |
| 分析块 `RequestAnalysisInit` | `⌈h/1KB⌉KB`（变长） | 1/2/4/8/16KB 阶梯类 |
| 请求副本 `RequestComeMain` | `⌈len/1KB⌉KB`（变长，可达 512KB） | 阶梯类 + `>64KB` 走大对象（或 413 上限） |

> 也就是说：**固定尺寸走分类链、变长走"2 的幂阶梯类"、超大走大对象**，全程不需要位图/扫描/压缩。
> 这正是老 `MemoryPool` 的思路（它就是分类空闲链），只是老版带锁；把它改成线程私有即可——
> 同时也解释了你现在的"整池归零"新池为什么反而退化：它把"按块回收"换成了"按 2MB 回收"。

## 五之三、分类空闲链的利用率问题（40B ~ MB 跨度）

> 追问："几十字节 / 几百字节 / KB / MB 混在一起，分类链怎么保证空间利用率？"——**问得对，分类链有两笔利用率账**。

### 两笔账

1. **内部碎片（阶梯步长）**：请求 r 落到类 S，浪费 `(S-r)/S`。2× 阶梯最坏 50%，1.25× 约 20%，1.1× 约 9%；
2. **容量切死（类之间不能互借）**：每类预分一块区域，某类用光时即便别类大量空闲，也只能 503。

### 实测（`/tmp/bm9.c`：40B/300B/1KB/4KB/20KB/100KB 混合，arena 32MB，每类均分）

| 流量 | 方案 | 内部利用率 | 因"本类容量不够"的失败数 |
|---|---|---|---|
| 均衡 | 精确分类链（每尺寸一类） | **100%** | 2 667 |
| 均衡 | 2× 阶梯分类链 | **77%** | 3 479 |
| 大块为主 | 精确分类链 | **100%** | 13 669 |
| 大块为主 | 2× 阶梯分类链 | **77.7%** | 16 714 |

（同一张表里位图方案的数字不可比 —— 它按 1KB 页取整：40B→1KB 只剩 3.9%，但按**字节加权**仍约 96%，因为字节量主要在 20KB/100KB 那些对象上；它的优点是容量全共享、没有"本类不够"的失败。）

**结论很清楚**：精确分类的内部浪费是 **0**，但"容量切死"会造成失败；阶梯分类在浪费和类数之间折中。

### 但对 c_web 来说，这笔账不成立

c_web 现有 5 个分配点**全部是 1KB 的整数倍**：

| 分配点 | 大小 | 1KB 步进类的浪费 |
|---|---|---|
| 分析块 | `⌈h/1KB⌉KB` | **0** |
| 判定块 | 2KB | **0** |
| 发送指针块 | `⌈n·sizeof(entry)/1KB⌉KB` | **0** |
| 响应头块 | 63KB | **0** |
| 请求副本 | `⌈len/1KB⌉KB` | **0** |

也就是说：**用 1KB 步进的类，内部碎片是 0**（你现在的代码里根本没有"几十字节"的块）。
"容量切死"用**每类 chunk 增长**解决：类不够时向共享 arena 要一个 chunk（如 64KB~1MB）切成该类块，
某类 chunk 全空可退回；再用一个总配额兜底，防止某一类吃光。

### 如果将来真的要放 40B/300B 这种小对象

分三层即可，仍然是 O(1) 无扫描：

| 尺寸段 | 做法 | 最坏内部浪费 |
|---|---|---|
| 8B ~ 512B | 细分小类：8/16/32/64/128/256/512（或 8B 步进位图） | ≤ 50%（小对象，绝对浪费小） |
| 1KB ~ 64KB | 1KB 步进类（正好覆盖 c_web 现有尺寸） | ≤ 1KB |
| > 64KB | 1KB 页位图 / 大对象直通 | ≤ 1KB + 位图共享容量 |

**一句话**：利用率不是靠"一个算法"保证的，而是靠**分层**：小对象细分、中段 1KB 步进、大块走页位图；
再叠加"每类 chunk 增长 + 总配额"，就能同时拿到 O(1) 分配和可接受的利用率。

## 五之四、"1MB 一块 × 1GB" 大配置实测（利用率 / 并发 / 速度）

基准 `/tmp/bm10.c`：负载 2KB(60%)+6KB(40%)、随机释放、100 万步；
**利用率 = 峰值活跃字节 / 触碰过的字节**（触碰过的页 = 会被算进 RSS 的页）。

| 方案 | 速度 | 失败数 | 6.7MB 活跃时触碰 | 利用率 |
|---|---|---|---|---|
| A. 你的池 **1MB×1024 = 1GB** | 33~49 ns | **0** | **43 MB** | **15.6%** |
| A'. 你的池 2MB×8 = 16MB（现状） | 33~55 ns | **1188** | 16MB（满） | 16% |
| B. 分类链（1KB 步进，chunk 1MB） | 35~58 ns | **0** | **6.79 MB** | **98.6%** |
| C. 位图（按"上次分配位置"提示） | **41~45 ns** | 0 | **1024 MB** | 0.7% |
| C'. 位图（按"最低空闲页"提示） | 79~169 ns | 0 | 8 MB | 83% |

### 三个结论

1. **1MB×1024（1GB）确实治好了"饿死"**：0 次失败（现状 2MB×8 在 3000 并发下 **1188 次失败**）。
   原因：1024 个子池里任意时刻只有少数几个在活跃，闲下来的子池能等到"计数归零"并复位。
2. **但代价是"摸过的内存是峰值的 6.4 倍"**：6.7MB 活跃 → 触碰 43MB（跑得越久摸得越多，最终会摸到 1GB）。
   因为 bump 分配 + 只在归零时复位，**摸过的页不会还给系统**（除非对空闲子池 `madvise(MADV_DONTNEED)`）。
3. **位图那一行揭示了真正的权衡**：想复用低位空洞（利用率↑）就必须从低处扫描 ⇒ 速度 41→79~169 ns；
   **分类链之所以两全（98.6% + 35~58 ns），是因为它根本不需要扫描**——链头就是可用的。

### 关于"1KB 是随便设的、实际大小有大有小"

- 关键不是"容器多大"，而是"**块大小是否和请求大小匹配**"；
- 你的池里 `perSize` 只是**容器**大小，块按请求大小 bump ⇒ 1MB 子池里 2KB/6KB/63KB 混放，
  **一个活块就能钉住整个 1MB**（回收要等归零）⇒ 利用率天然上不去；
- 分类链是**按请求大小分池**（块 = 请求）⇒ 0 内部碎片 + free 立刻复用 ⇒ 98.6%；
- 尺寸跨度大时用阶梯（1.25× 步长浪费 ≤20%，2× 步长 ≤50%）；**c_web 现有尺寸全是 1KB 整数倍 ⇒ 1KB 步长浪费 = 0**。

### 若坚持用大池，必须同时做三件事

1. 子池 ≤1MB 且数量 ≥512（解决饿死）；
2. 空闲子池 `madvise(MADV_DONTNEED)`（或每子池单独 `mmap`）把页还给系统，否则 RSS 会一路涨到 1GB；
3. 把 2KB / 6KB / 63KB **拆成不同池**（混放是碎片与"钉住"的根源）。

## 五之五、"小请求能不能用大页？" 以及"结论是不是只在爆满时成立？"

### 1. 小请求用大页——可以，而且推荐；**问题不在页大，在"以页为回收单位"**

- 你的池现在：页 = 1~2MB，**回收单位也是页**（`hadAllocNum` 归零才整页复位）⇒
  2KB 的块确实放在 1MB 页里，但它的空间只有**整页归零**时才复用 ⇒ 一个活块钉住整页 ⇒ 利用率低、易饿死；
- 正确做法：**页照旧大（甚至用 2MB 大页/THP），但页内按 size class 管理、按块回收**。
  实测里我的 B 方案就是 "chunk=1MB 的大块里切 2KB/6KB 小块 + 空闲链" ⇒ **利用率 98.6%**、35~58 ns；
- 大页还有额外好处：16MB 池用 2MB 页只需 8 个 TLB 项，用 1KB 页要 16k 项 ⇒ **大页 + 页内块级管理是最优组合**；
- 反过来：如果只有"1MB 一个类"而请求是 2KB，利用率 = 0.2%（所以必须有阶梯类，不能只有大页）。

### 2. 结论不是"只在爆满时成立"

| 场景 | 你的池（1MB×1024） | 分类链 |
|---|---|---|
| **低负载**（0.8MB 活跃） | 利用率 **11.5%** | **90.3%** |
| 中负载（6.7MB 活跃） | 15.6% | 98.6% |
| 真实服务器 c=200（1.6MB 活跃 / 16MB 池 = 10% 占用） | **大面积 503** | — |

- 基准里 `cap=200/1500/3000/20000` 只是**放大差异**用的；
  但**低负载那一行差距反而更大**（11.5% vs 90.3%），说明结论不是靠"堆满"堆出来的；
- 真实压测也一致：c=50 时 54k QPS、RSS 2.6MB 一切正常；**c=200 时活跃仅 1.6MB / 池 16MB 就开始 503**
  —— 这是"回收策略"的问题，不是容量不够的问题。

## 五之六、分类链是"改造"还是"重写"？你的池子能不能分类？

**结论：改造，不是重写。** 你现在的 `Memory_Pool + Memory_Entry[]` 结构恰好就是分类链需要的"容器 + chunk 表"，
只要把"每个 entry = 一个 bump 区"改成"每个 entry = 一个**专属某个尺寸类**的 chunk"即可。
`MemoryPoolInit / MemoryPoolAlloc / MemoryPoolFree` 三个 API 和调用点都可以保持不变。

### 对照表

| 现在 | 改造后 |
|---|---|
| `entry` = 1MB/2MB 的 bump 区 | `entry` = 1MB **chunk，专属一个 size class** |
| 块按请求字节 bump（混放） | chunk 内按 `blkSize` 切块（同类等大） |
| `hadAllocNum` 归零 → 整 chunk 复位 | **free → 块挂回该类空闲链（立刻可复用）** |
| `freeSize/allocPtr` 单调前进 | 只在 chunk 首次切块时用；之后走空闲链 |
| `hint` = 上次用的 chunk | `hint` = 上次用的类（或 chunk） |
| （无） | `void* freelist`（块前 8B 当 next） |

### 具体改动清单（约 150~250 行，不改调用点）

**保留**：`Memory_Pool`、`beginPtr/endPtr/manageEntry[]`、一次性 `malloc` 大块、线程私有、无锁、
`MemoryPoolFree(pool, ptr)` 不需要尺寸、`notfull` 出参（供上层 503）。

**新增/改动**：

```c
typedef struct Memory_Entry{
    char* beginPtr;
    char* allocPtr;      /* 仅 chunk 首次切块时用 */
    int   freeSize;
    int   totalSize;
    int   blkSize;       /* ★ 新增：本 chunk 服务的块大小（该类的块大小） */
    void* freel;         /* ★ 新增：本 chunk 的空闲块链头 */
    int   usedBlocks;    /* 可选：统计/归还整 chunk 用 */
}Memory_Entry;

/* ★ 新增：类 → 当前可用的 chunk 索引（或直接用 hint 扫 manageEntry） */
static int classChunk[NCLS];
```

- `MemoryPoolAlloc(p, needSize, &ptr, &notfull)`：`blk = 阶梯(needSize)`（1KB 步进覆盖你现在的 2KB/6KB/63KB/请求副本）；
  先取该类 `freel`；空则拿一个空 chunk、设 `blkSize`、把整块切成等大块挂到 `freel`，再取一个返回；
- `MemoryPoolFree(p, ptr)`：`entry = (ptr - beginPtr) / perSize`（你现在就是这么算的）；
  取 `manageEntry[entry].blkSize`；`*(void**)ptr = freel; freel = ptr;` —— **不再需要"归零复位"**；
- `MemoryPoolInit(p, chunkSize, chunkNum)`：签名不变，内部初始化类表即可（类表可以用宏/静态表，不用改调用点）。

**删掉/降级**：`hadAllocNum` 的"归零复位"逻辑（保留做统计也行）、`MemoryEntryAlloc` 的"装不下就标记满"逻辑。

### 你的池子能否分类？——能，而且天然适配

1. 你的 `Memory_Entry` 已经有 `beginPtr/allocPtr/freeSize/totalSize`，**chunk 的骨架已经在了**；
2. 你的 `free(ptr)` 已经用"指针落在哪个 entry"定位（`gap >> ctz(perSize)`）——分类后这个定位仍然成立，只是**再除一次 `blkSize`** 得到块号；
3. 你的"线程私有、无锁"前提完全保留（类链也是线程私有的）；
4. 你的"大块一次性 malloc"也保留（chunk 仍然从一个 1GB/16MB 的大块里切）。

### 唯一要新增的设计：容量在类之间分配

- 方案 A（简单）：`chunkNum` 按实测比例预分（例如 1KB 类 2 个 chunk、2KB 类 4 个、6KB 类 8 个、63KB 类 4 个）；
- 方案 B（推荐）：**chunk 池**——所有 chunk 先不归属任何类，某个类需要时领一个（设 `blkSize` 并切块），
  该 chunk 的块全部归还后可以退回池子给别的类用 ⇒ 容量自适应，且不会"一类吃光"（加总配额即可）。

> 一句话：**你的容器和 API 都不用推倒，改的是"entry 的语义"和分配/释放两个函数体**；
> 这也是为什么它能同时拿到 98.6% 利用率、35~58 ns、0 失败，而不需要位图/扫描/压缩。

**只有 4 种尺寸，全部是 1KB 的整数倍**（1KB 分析块 / 2KB 判定块 / 6KB 发送指针块 / 63KB 响应头块）。

这条数据直接回答了两个质疑：

### 1. "分类链的利用率是不是靠你挑负载？"

不是。按真实尺寸分布，**1KB 步进类的内部浪费 = 0**（每个尺寸都正好落在类边界上）。
如果按字节加权，**63KB 那一类占了 86% 的字节量**（36.5GB / 42.5GB）——所以"利用率"的主战场是 63KB 块，而不是几十字节。

### 2. "你的池子在 c=200 饿死是不是负载太极端？"

不是，而且现在有了更硬的解释：

- 2MB 子池 / 63KB 头块 ≈ **32 块/子池**；8 个子池合计 ≈ **260 块**；
- 也就是整个 `txt_pool`(16MB) 只够 **~260 个请求同时在途的头块**；
- c=200 时在途请求 ~200 ⇒ **已用掉 77% 的池容量**，任何一个长寿块没有归还，就立刻进入"分不出 63KB"的状态 ⇒ 大量 503；
- 而 63KB × 50k QPS = **3.1 GB/s 的分配吞吐** ⇒ 每个 2MB 子池 ~0.6ms 就被填满一次，
  "等整池归零再复用"在 50k QPS 下几乎等不到。

**结论**：c=200 的 503 是"**块级需求 260 块 vs 池容量 260 块 + 回收靠整池归零**"的结构问题，
与"我的基准把负载堆满"无关；低并发（c=50）时之所以健康，是因为在途块只有 ~50 个、池还有 4 倍余量。

### 顺带：这也说明 63KB 头块是最该被"块级回收"的对象

它是字节量的大头（86%）、每请求一个、数量恒定 ⇒ 分类空闲链里就是"63KB 类"那一条链，
`free` 立刻可复用，不需要等 2MB 子池清空；容量按 `63KB × 在途请求数` 预留即可（c=200 ⇒ ~13MB）。

基准 `/tmp/bm11.c`：每个配置单独进程、`malloc(1GB)` 惰性映射、**每块按 4KB 页真实写入**（模拟服务器写请求/响应字节），

## 五之九、按"真实小尺寸（不再补到 1KB）"重算：块浪费 vs 真实 RSS

基准 `/tmp/bm12.c`：每块真实写页、读 `VmHWM`；**输入不再补 1KB**。
"块浪费" = 1 − Σ请求字节 / Σ块字节（内部碎片，**不含**回收问题）；
"真实利用率" = 峰值活跃字节 / VmHWM（**含**回收问题）。

### 负载 1：精确混合（96~448B 占 56%，2KB 15%，6KB 15%，63KB 14%），c=200，峰值活跃 3.03MB

| 方案 | ns/次 | 失败 | **VmHWM** | 真实利用率 | **块浪费** |
|---|---|---|---|---|---|
| 你的池（精确字节） | 65.7 | 0 | **16 MB** | 18.9% | **0.0%** |
| 分类链（2× 阶梯） | **53.5** | 0 | **5 MB** | **60.5%** | 4.7% |
| **分类链（1.25× 阶梯）** | 64.4 | 0 | **5 MB** | **60.5%** | **1.5%** |
| 位图（1KB 页） | 139.0 | 0 | 17 MB | 17.8% | 3.9% |
| 位图（64B 页） | 735.9 | 0 | 13 MB | 23.3% | **0.2%** |

### 负载 2：小对象 24~512B（一半 <128B），c=2000，峰值活跃 0.35MB

| 方案 | ns/次 | VmHWM | 真实利用率 | **块浪费** |
|---|---|---|---|---|
| 你的池 | 62.3 | 6 MB | 5.8% | 2.0% |
| 分类链（2× 阶梯） | **53.3** | **2 MB** | **17.3%** | 24.8% |
| **分类链（1.25× 阶梯）** | 59.1 | **2 MB** | **17.3%** | **10.8%** |
| 位图（1KB 页） | 54.3 | 3 MB | 11.5% | **80.6%** |
| 位图（64B 页） | 277.2 | 2 MB | 17.3% | 12.9% |

### 五条结论（这次把两笔账分开算，不混在一起）

1. **你的池内部浪费确实是 0**（精确字节 `needSize+4`）——这一点我之前没有否认；
   但它的代价是**真实 RSS 16MB / 活跃 3MB = 5.3 倍**（bump + 整池归零，摸过的页不还）。
2. **1KB 页位图对小对象浪费 80.6%** —— 你担心的"几十字节补到 1KB"正是这个；
   把页降到 64B 能压到 12.9%，但速度掉到 **277~736 ns**（每块要多做几十~上千次位操作）。
3. **分类链 1.25× 阶梯是唯一两个指标都好的**：块浪费 **1.5%（混合）/10.8%（小对象）**，
   VmHWM **5MB / 2MB**（比你的池省 3 倍），速度 53~64 ns（**不输**你的池 62~66 ns ——
   因为你的池在混合尺寸下 `hint` 经常失效，要线性扫 1024 个 entry）。
4. **所以"补全"要改的地方在调用方**：`RequestComeMain.c` 的 `(h_size/1024+1)*1024`、
   `WorkerThread.c` 的 `4*size`；池子按 1.25× 阶梯分类、chunk 下限 16KB（不是 1MB）。
5. **大对象（>64KB）才适合页位图**；小对象用页一定浪费（1KB 页 80.6%，64B 页虽省但慢）。

## 五之十、QPS 瓶颈定位（实测：谁在吃 CPU、每请求多少 syscall）

### 1. 逐线程 CPU（`/proc/PID/task/*/stat` 采样，5 秒窗口，2 vCPU）

| 并发 | QPS | 接待线程 | worker1 | worker2 | 进程合计 | 每请求 CPU |
|---|---|---|---|---|---|---|
| 50 | 55 465 | **81.6% 核** | 12.2% | 11.0% | 104.8% 核 | **18.9 µs** |
| 100 | 53 020 | **79.0% 核** | 13.4% | 9.0% | 101.4% 核 | **19.1 µs** |

⇒ **接待线程一个人吃掉 80% 核，两个 worker 各 10%，另一个 vCPU 有 ~0.95 核闲置但用不上**。
天花板可以这样估：1 核 ÷ 14.7 µs（接待线程每请求 CPU）≈ **68k QPS**，与实测峰值 6.2 万吻合。

### 2. 每请求的 syscall 清单（`strace -c -f`，6500 个请求的窗口）

| syscall | 次数/请求 | 说明 |
|---|---|---|
| **futex** | **1.87** | 任务队列/响应队列的 sem + mutex ⇒ **每请求两次上下文切换**（77% 的 syscall 时间） |
| read | 2.06（含 1 次 EAGAIN） | 读请求 + 一次空读 |
| write | 2.01 | 响应 + eventfd 唤醒 |
| epoll_ctl | 1.02 | 每发一个响应就 MOD 一次读/写事件 |
| epoll_wait | 0.06 | 事件驱动，正常 |

⇒ 每请求 **~7 次 syscall**，55k QPS ⇒ ~38 万次/秒；futex 带来的上下文切换是最大单笔开销。

### 3. 每请求 19 µs 的大致构成（按代码路径）

1. `epoll_wait` 返回后的 `read` + `RequestIntergrity` 状态机解析；
2. **拷贝两次**：socket → 暂存池（`RequestTempPool`）→ 请求副本（`http_pool`）；
3. 队列投递（sem_post + eventfd）→ worker 唤醒（futex）；
4. worker 侧：`RequestGet` 再拷一次进分析块 + 解析 + 处理；
5. 回程：`ReceiverQueue`（mutex+sem）→ `GetAndJudge`（fd 表查找、send 指针池、搭便车 free）→ `write` → `epoll_ctl(MOD)` → `TimerReset`。

### 4. 结论：限制 QPS 的是这三件事（与内存池无关）

| 排序 | 因素 | 证据 | 能不能改 |
|---|---|---|---|
| ① | **单接待线程串行化** | 81.6% 核 vs worker 12%/11%，另一核闲置 | 能：多接待线程 / `SO_REUSEPORT` 多进程各自 epoll ⇒ 近似线性 |
| ② | **每请求 2 次 futex（队列信号量）** | syscall 时间 77% 在 futex | 能：批量投递、无锁 SPSC + 只在"空→非空"时唤醒、worker 一次取多个任务 |
| ③ | **每响应 1 次 `epoll_ctl(MOD)` + 1 次 write** | 1.02 次/1.02 次 | 能：边沿触发 + 只在 EAGAIN 时加 EPOLLOUT；`writev` 合并流水线响应 |
| — | 两条拷贝（暂存→副本、副本→分析块） | 代码路径 | 能：解析直接在暂存区做、或零拷贝交接 |

> 注意区分：**c≥160 时吞吐腰斩 + 大面积 503 是"池子容量/回收"问题**（见 §5.1~5.5），不是 CPU 瓶颈；
> 修好池子后会回到"单接待线程"这条 CPU 天花板。

## 五之十一、对照 nginx：为什么它能做到几十万 QPS

### 1. 先纠正前提：nginx 不是"单线程"

- nginx = **多 worker 进程（通常 = CPU 核数）+ 每个 worker 一个单线程事件循环**；
- 所以"几十万 QPS"是 **N 个 worker 叠加**的结果。**单个 worker** 在 keep-alive + 小静态响应下大约是 **3~8 万 QPS**，
  和本服务实测天花板（~6.2 万/核）**是同一个量级**；
- 差别在于：nginx 能把这份单核能力**线性复制到所有核**（`SO_REUSEPORT` 每 worker 独立 accept 队列），
  而本服务所有 IO 都串在**一个**接待线程上（实测 81.6% 核，另一个 vCPU 闲置）。

### 2. 单核成本差在哪（本服务 19 µs/请求 vs nginx ~1~2 µs）

| 环节 | 本服务（实测） | nginx 做法 | 省下的量级 |
|---|---|---|---|
| 线程间交接 | **1.87 次 futex/请求**（任务队列 + 响应队列的 sem/mutex）⇒ 约 2 次上下文切换 | **无**：accept→read→parse→write 全在同一 worker 线程内 | 3~5 µs |
| epoll 事件管理 | **1.02 次 `epoll_ctl(MOD)`/请求** | 边沿触发 + 状态机，只在必要时改关注事件（常见 0~1 次） | ~1 µs |
| 写响应 | 每个响应 **1 次 `write`**（另 1 次 eventfd） | 头+体用 **`writev` 一次**；静态文件 **`sendfile`** | ~1 µs |
| 请求拷贝 | **2 次 memcpy**（socket→暂存池→请求副本，worker 里再拷进分析块） | **原地解析**（只在接收缓冲里记指针/长度），零拷贝 | 1~2 µs |
| 解析 | `strstr("\r\n\r\n")` + 逐头 `strchr` | 状态机 + 查表（`ngx_http_parse_request_line`），单遍 | ~1 µs |
| 内存 | 每请求 4 次池分配（1KB/2KB/6KB/63KB）+ 4 次释放；63KB 块导致池按 2MB 子池快速填满 | **连接级 pool**（`ngx_pool_t`），请求间复用；响应头用预生成模板 | 池本身只要 ~0.1 µs，但 63KB 块带来容量问题 |
| 定时器 | 每响应 `TimerReset`（堆删+插） | rbtree + 缓存时间（`ngx_time_update`） | ~0.3 µs |
| accept | 每连接 1 次 accept | `accept4` 循环批量取 + SOCK_NONBLOCK | 连接建立时一次性 |

> 上表里"省下的量级"是**按 syscall/上下文切换的常见单价估算**（并非全部实测）；
> 实测部分是：19 µs/请求、81.6% 单线程占比、1.87 futex、1.02 epoll_ctl、2.06 read、2.01 write。

### 3. 若照 nginx 的路子改，本服务的上限在哪

| 改动 | 预期 | 备注 |
|---|---|---|
| ① 多接待线程/多进程 + `SO_REUSEPORT` | ×N（2 核 ⇒ ~2×，10 万+） | 唯一能线性扩展的 |
| ② 去掉线程间队列（或批量 + 批边界唤醒） | 每请求省 3~5 µs | 需要把"解析/处理"和"IO"放在同一线程，或改成无锁批量 |
| ③ 边沿触发 + 只在 EAGAIN 时关注写 | 省 1 次 syscall | 改动小 |
| ④ `writev` 合并响应 | 省 1 次 syscall/响应 | 流水线场景收益更大 |
| ⑤ 原地解析 + 零拷贝交接 | 省 1~2 µs | 需要改解析器接口（指针/长度而非拷贝） |
| ⑥ 连接级 pool（请求间复用） | 省 4 次池操作 + 消除 63KB 块的池压力 | 与本报告的"分类链"可以共存 |

**保守估计**：②~⑥ 做完，19 µs ⇒ **7~9 µs/请求**（单线程 11~14 万 QPS），再叠加 ① 的 N 个接待线程。

## 五之十二、"多开几个线程行不行"——实测与前提

### 1. 实测：双实例（不同端口）在本机 2 vCPU 上几乎不涨

| 配置 | QPS | CPU |
|---|---|---|
| 单实例（1 接待线程 + 2 worker） | **55 744** | 98% 核（进程内） |
| 双实例各自 -c50 | 30 312 + 27 322 = **57 634** | 服务器共 120% 核 |
| 双实例复测 | **57 802** | **整机 197%（2 核几乎打满）** |

⇒ 双实例只比单实例多 **3%**，而"整机 CPU=197%"说明：**瓶颈已经变成压测工具（wrk 2 线程）+ loopback 软中断**，
不是服务器本身。**在本机同压的环境里，任何线程数都突破不了 ~5.8 万**，所以这个实验**测不出**多线程的真实收益。

要验证真实扩展性，必须换一台机器跑压测（或 4~8 vCPU），否则测的是测试机的天花板。

### 2. 哪些"线程"有用、哪些没用

| 加什么 | 有用吗 | 为什么 |
|---|---|---|
| 多开 **worker** 线程 | ❌ 没用 | worker 现在只占 10~13%；加线程只增加唤醒/futex/切换 |
| 多开 **接待线程**（IO 线程） | ✅ 理论上线性 | 但要解决 4 个共享点（见下） |
| 多开**进程** + `SO_REUSEPORT` | ✅ 最容易 | 每进程独立 epoll/fd 表/定时器/池，零共享 |

### 3. 多接待线程/多进程必须解决的 4 个共享点

1. **accept**：`SO_REUSEPORT`（每个进程/线程一个 listen socket）或 `EPOLLEXCLUSIVE`，否则惊群；
2. **fd 表 / 定时器 / 连接状态**：必须**按线程分片**（shard），不要靠加锁；
3. **队列**：现在是一对一 SPSC（接待→worker、worker→接待）；多接待线程后要变成"每 shard 一组"，
   否则 MPSC 的锁会把刚省下的 futex 又加回来；
4. **内存池**：每线程一套（内存 ×N），而且**每个线程的池都会独立出现 c=200 的 63KB 饿死** ⇒
   必须先把"块级回收"修好，否则多开只是把 503 复制 N 份。

### 4. 性价比：先砍每请求成本，再扩线程

| 路线 | 收益 | 代价 |
|---|---|---|
| 砍 futex/epoll_ctl/拷贝/解析（19µs → 10µs） | **~2×**（单线程 10~11 万） | 不改架构 |
| 多进程 + SO_REUSEPORT | ×N（受核数/网卡限制） | 改架构 + 内存 ×N + 池问题放大 |

> 顺序建议：**先 0 成本优化每请求成本，再上多进程**；两者叠加才有"几个线程 × 10 万"的效果。

### 五之十附：一次更细的打点，以及对我上一条的更正

在接待线程/收包路径里插桩（`clock_gettime` 打点，c=50，QPS≈52k）：

```
[PROBE_C] total=10149ns | find=49  read=1227  parse=408  copy=63  push=8285 ns
[PROBE_Q] push=400000  avg_total=68ns  avg_lockwait=40ns  队列满=0(0.00%)  峰值深度=49
```

**更正**：上面那个 `push=8285ns` 是**墙钟**差，里面混进了**被抢占的时间**（2 vCPU 上跑 3 个服务器线程 + wrk）。
单独量 `TasKQueuePush` 本身只有 **68 ns**（锁等待 40 ns、队列从未满、峰值深度 49/100）。

**可靠的结论**（不依赖墙钟拆分）：

| 项 | 实测 | 说明 |
|---|---|---|
| 用户态代码 | `parse` 408 ns、`copy` 63 ns、`push` 68 ns、`find` 49 ns | **都很便宜，不是瓶颈** |
| `read` 系统调用 + 拷入暂存区 | 1.2 µs | 真金白银 |
| 每请求 syscall | **7 次**（1.87 futex / 2.06 read / 2.01 write / 1.02 epoll_ctl） | 主要成本 |
| 每请求 CPU | 19 µs（接待 14.7 + worker 2×2.2） | 接待线程串行 |

⇒ **14.7 µs 主要花在"系统调用 + 唤醒/上下文切换"上，而不是用户态的解析/拷贝/入队。**
所以优化顺序应该是"减少 syscall 次数与唤醒次数"，而不是去优化 `TasKQueuePush` 或解析。
（strace 下 futex 占 77% 是**被 strace 放大**的比例，只用于看"次数"，不能看"时间"。）

## 五之十三、"接待线程多线程化 + worker 线程池"的锁竞争量级（实测）

微基准 `/tmp/bm_queue.c`：与现有实现同构的 **mutex + 2 个信号量** 队列（容量 100），测每次"投递+取走"的成本。
（2 vCPU 上跑 2~8 线程，绝对值偏大，但**随线程数的变化趋势**是关键。）

| 配置 | 吞吐 | **每次交接** | 系统态 CPU | 说明 |
|---|---|---|---|---|
| 1 生产 / 1 消费（共享队列） | 6.67 M ops/s | **150 ns** | 69% | 无竞争基线（≈ 现有队列实测 68ns 的同量级） |
| 2 生产 / 2 消费（共享队列） | 0.96 M ops/s | **1 046 ns** | **126%** | 竞争来了：**7 倍**，系统态 CPU 爆掉 |
| 4 生产 / 4 消费（共享队列） | 0.97 M ops/s | **1 035 ns** | 42%（被 2 核限制） | 仍 ~1 µs |
| 2 生产 / 4 消费（共享队列） | 0.32 M ops/s | **3 129 ns** | 120% | 生产/消费不匹配 ⇒ **20 倍** |
| 4 生产 / 2 消费（共享队列） | 0.39 M ops/s | **2 559 ns** | 93% | 同上 |
| 4 生产 / 4 消费（**每对一条队列**） | 2.41 M ops/s | **415 ns** | 99% | 分片后回到亚微秒 |

### 结论（按 QPS 量级算总账）

| 目标 QPS | 每请求交接次数 | 共享一把锁（1 µs/次） | 分片（0.15 µs/次） |
|---|---|---|---|
| 5.5 万（当前） | 4（任务/响应/回收/唤醒） | 0.22 核 | 0.03 核 |
| 30 万 | 4 | **1.2 核（全被锁吃掉）** | 0.18 核 |
| 100 万 | 4 | 4 核 ✗ | 0.6 核 |

⇒ **锁竞争在你当前 QPS 下不是瓶颈**（实测 `TasKQueuePush` 68ns、队列从未满），
但**它是"加线程后的新瓶颈"**：线程越多，每次交接越贵（150ns → 1~3µs），收益会被吃掉。

### 因此架构建议

1. **分片（thread-per-core）**：每核一组"接待线程 + 自己的队列 + 自己的 worker"，**零共享**；
   队列天然是 SPSC ⇒ 150ns 级，且缓存局部性最好；
2. 如果一定要共享池：**无锁 MPSC + 批量投递**（一次投 8~16 个任务 + 一次唤醒），
   把"每请求 1 次交接"摊薄成"每 16 请求 1 次"；
3. **能不分发就不分发**：像 nginx 那样在 IO 线程内处理轻量请求，只把阻塞操作（文件 IO、DB）交给线程池；
4. worker 池大小：按现有数据 worker 每请求只用 **2.2 µs CPU**，2~4 个就够；
   加 worker 只增加锁竞争和上下文切换。

## 五之十四、"1 接待 : 1 worker + 显式阻塞池"方案评估

### 1. 它解决了什么、没解决什么

| | 影响 |
|---|---|
| ✅ **解决锁竞争** | 1:1 之后队列变成 SPSC：交接 **150 ns**（实测）vs 共享 M:N 的 **1~3 µs** ⇒ 30 万 QPS × 4 次交接：**0.18 核 vs 1.2 核**，省下约 1 个核 |
| ❌ **没解决每请求 14.7 µs** | 接待线程仍然是 read/parse/write/epoll_ctl 的串行点；交接只占其中 0.2~0.3 µs（当前 QPS 下） |
| ✅ **handler 可以阻塞了** | 但必须改成"submit + continuation"，否则 worker 被阻塞会拖住整对 |

### 2. 必须处理的 5 件事（否则会引入新 bug）

1. **队列 SPSC 无锁**：单生产者/单消费者用 head/tail 索引 + 环形缓冲即可，不需要 mutex/sem；
2. **handler 不得阻塞**：阻塞操作 `Submit(pool, work, on_done)` 后立刻返回；该请求的槽位/序号
   （`pack_in_path`、`serial`）必须保持占用，否则响应顺序和流控会乱；
3. **完成回调的扇入**：pool 的 N 个线程要向 M 个接待线程回结果 ⇒ 两种做法：
   - 每接待线程一个 **MPSC 环**（多生产者，需要无锁 MPSC）；
   - 或每 pool 线程一个 **outbox**，接待线程轮询/被唤醒后 drain（简单、无锁，drain 成本 O(N)）；
4. **请求副本的所有权**：你现在的池是**线程私有、无锁**的，pool 线程**不能** free 接待线程池里的块。
   完成回调只能把指针（`httpNeedFree`）回传给拥有它的线程，由它"搭便车"释放；
5. **超时与背压**：`pack_in_path < ed_store_blocknum` 已限制单连接在途；
   还需要限制"池里在途任务总数"，池满时对新任务返回 503/排队，避免反压到所有连接。

### 3. 一个更彻底的变体（我更推荐）

实测：**解析 0.4 µs、worker 总耗时 2.2 µs**，而接待线程 14.7 µs。
既然 handler 很轻，不如：

> **接待线程自己跑 handler**（IO + 解析 + 业务都在同一线程）⇒ **每请求 0 次交接**（省 2~4 µs），
> 只有 handler 明确要阻塞时才 `Submit` 到线程池 ⇒ 这正是 nginx 的做法。

1:1 的 worker 可以保留，但只用于"重活/可并行"的处理（压缩、模板渲染、磁盘读）。

### 4. 建议的落地顺序

| 步骤 | 内容 | 预期 |
|---|---|---|
| 0 | 砍 syscall：去 `epoll_ctl(MOD)`、`writev` 合并、少一次 EAGAIN read | 14.7 → ~9 µs |
| 1 | 队列改 SPSC 无锁（1:1 或分片） | 交接 68ns→30ns 级；为高 QPS 铺路 |
| 2 | handler 内联到接待线程（轻请求） | 每请求省 2~4 µs |
| 3 | 阻塞池 + submit/continuation（含扇入与所有权规则） | 阻塞不拖累整对 |
| 4 | 多接待线程/多进程 + `SO_REUSEPORT` | ×核数 |

## 五之十五、"以后把这个组合开多个"：现在就要埋好的 6 个点

### 1. 两种形态

| 形态 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **多进程** | 每个进程 N 对（接待+worker），`SO_REUSEPORT` 各自 listen | 零共享、最稳、崩溃隔离 | 内存 ×进程数（池要按进程缩小） |
| **单进程多对** | 每对一套 epoll/fd表/定时器/队列/池 | 共享缓存方便 | 必须把所有全局改成"每对一份" |

### 2. 必须预先去掉的共享点（现在做最省事）

1. **`taskQueue` 是全局的**（`GlobalResource.c` 里 `Task_Queue* taskQueue;`）⇒ 多对会共用一条队列，
   立刻退回"共享锁 1~3 µs"。**必须改成 `pair->task_q`**（1:1 时就是 SPSC）。
2. **accept**：每对一个 listen socket（`SO_REUSEPORT`）或 `EPOLLEXCLUSIVE`；否则所有对抢同一个
   listen fd（惊群），或者只有一个对能 accept。
3. **fd → 对 的归属必须固定**：靠 `SO_REUSEPORT` 的 4 元组哈希 + 该对 accept 来保证；
   连接一旦归某个对，就永远不再跨对（这样 fd 表/池都不用加锁）。
4. **定时器 / fd 表 / store_area / http_pool / txt_pool**：每对一份（现在这些已经是线程私有的，
   只要别在初始化时共用同一个对象）。
5. **统计与日志**：不要用全局计数器（热路径上会变成一条共享缓存行）；用每对 TLS 计数 + 周期性汇总。
6. **`ed_store_blocknum`**：它决定单连接在途上限，若它来自"全局已建立连接数"，多对时要按**每对**计算，
   否则连接多的对会被限得过死。

### 3. 池容量要按"每对并发"重算

c=200 总量、pairs=4 ⇒ 每对 ~50 连接：

| 类 | 每对需要 |
|---|---|
| 63KB 头块 | 50 × 63KB ≈ **3.2 MB** |
| 6KB 发送指针 | 50 × 6KB ≈ 0.3 MB |
| 2KB 判定块 | 0.1 MB |

⇒ 每对 4~8MB 足够（不需要 16MB，更不需要 1GB）；总内存仍然只 ~16~32MB。

### 4. 扩展性预期与"新墙"

- 有足够核 + 独立压测机时：pairs 数 ≈ 线性（每对 ~5.5 万 ⇒ 8 对 ~44 万）；
- 新墙会依次出现：**网卡队列/软中断**（多队列 + RPS 可解）、**内存带宽**（63KB 头块的触碰量）、
  **accept 偏斜**（`SO_REUSEPORT` 哈希在 keep-alive 下很均匀）；
- **本机 2 vCPU 测不出来**（实测双实例只 +3%，整机 197%）。

### 5. 现在就顺手能做的 5 个改动（为以后开多个铺路）

1. `TasKQueuePush(taskQueue, ...)` → 传 `pair->task_q`（把全局变成参数）；
2. 把 `ReveiverThreadMain` / `WorkerMain` 里所有对全局的引用收敛到一个 `struct Pair*`；
3. accept 循环用 `accept4(...SOCK_NONBLOCK)` 批量取，socket 上打 `SO_REUSEPORT`（先单对也安全）；
4. 统计改成每对累加，最后汇总打印；
5. 让"线程数 / 对数"来自配置而不是硬编码（`main.c` 里一眼可见）。

## 五之十六、"完全不交流的多对 + 业务线程分离 + 可调背压"：可行，但有 4 条硬前提

### 1. 这个方向是对的（业界叫 shared-nothing / thread-per-core + async offload）

- 每对独立 epoll / fd 表 / 定时器 / 队列 / 池 ⇒ **热路径零共享、零锁**（交接 150 ns 级）；
- 一对被阻塞只影响它自己那 1/N 的连接；
- 业务线程与 IO 线程分离 ⇒ 解析与业务可以按比例调资源、按水位施压。

### 2. 但"完全不交流"有 4 个容易被忽略的耦合点

| # | 隐藏耦合 | 不处理的后果 | 处理办法 |
|---|---|---|---|
| 1 | **阻塞线程池如果是全局的** | 池被打满时所有对一起卡 | 池按对独立；或全局池 + **按对配额 + submit 不阻塞**（满了直接 503/排队超时） |
| 2 | **accept 分布**（SO_REUSEPORT 4 元组哈希） | 少数重客户端把某一对压满，别对空闲 | 每对连接数上限；必要时 BPF 哈希 / 允许迁移连接 |
| 3 | **全局上限**（最大连接数、总内存） | 各对各自为政，OOM 或被内核限死 | 用**原子计数**做准入（原子不是锁，热路径可接受） |
| 4 | **日志/统计的全局 mutex** | 一条共享缓存行把 N 对串起来 | 每对 TLS 计数，汇总时再合并 |

### 3. 背压：把"队列满了塞 TempPack"换成"水位控制停读"（更平滑）

现在：`TasKQueuePush` 满 → 存 `TempPack` → 返回 0 → `RequestComeMain` 退出循环（等于丢一次读取机会）。
建议改成标准的**高低水位**：

```
每对维护 inflight（队列深度）:
  >= 75% 上限  →  关掉该连接的 EPOLLIN（不再 read），TCP 窗口自然反压客户端
  <= 25% 上限  →  重新打开 EPOLLIN
```

好处：不丢请求、不发 503、内存有界；客户端自然降速（这就是 nginx 的 `client_body_buffer_size` / 读事件开关思路）。

可调的四个旋钮（都建议做成配置）：

| 旋钮 | 作用 | 建议初值 |
|---|---|---|
| 每连接在途窗口 `ed_store_blocknum` | 单连接流水线深度 | 8~16 |
| 每对队列深度 | 吸收突发 | 256~1024 |
| 每对阻塞任务上限 | 防止池被一对吃光 | 8~16（超了 503） |
| 每对连接数上限 | 控制 accept 偏斜 | 总上限/N × 1.2 |

### 4. 用实测比例来"调解析与业务的比例"

实测每请求 CPU：**接待线程 14.7 µs（主要是 syscall/唤醒）｜worker 2.2 µs｜解析 0.4 µs**。

- 解析只占 **0.4/17 ≈ 2%** ⇒ **为解析加线程没意义**；
- 业务 2.2 µs ⇒ 业务比解析重 5 倍，但两者加起来只有 syscall 的 1/6；
- 所以"调比例"应该调的是：**接待线程的 syscall 数**（7 → 3~4）× **对数**，而不是 worker 数量。

### 5. 隔离的代价（要接受）

- 一对里的慢连接会占住该对的读事件（即使不阻塞业务），**该对吞吐下降**；
- 不接受 work stealing 的话，负载不均时总吞吐 = N × 最忙那对的速率；
- 兜底：① 每对连接数上限；② 慢连接（超时）主动断开；③ 极端情况允许"连接迁移"（那就回到少量交流）。

## 五之十七、"观测处理速率来调背压"：怎么做才不会晃，也不会瞎

### 1. 先说一个容易踩空的点：你的瓶颈在"生产者"一侧

实测每请求：接待线程 **14.7 µs**（syscall/唤醒为主），worker **2.2 µs**。
接待线程既是**生产者**（read + push），也是瓶颈 ⇒ **队列深度很可能一直是浅的**，
等你看到队列满时，延迟早就已经上去了（因为它自己就是慢的那一端）。

⇒ **只看队列深度/处理速率会失灵**，必须同时看"接待线程自己的循环耗时"与"请求在队列里的等待时间"。

### 2. 三条可用信号（按可靠性排序）

| 信号 | 怎么取 | 成本 | 适用 |
|---|---|---|---|
| **① 接待循环耗时**（epoll 返回到本批处理完） | 循环里取两次时间戳 | 2×25ns/批 | **最直接**（对"接待线程是瓶颈"最敏感） |
| **② 队列驻留时间**（push→pop） | push/pop 各打一个时间戳，或只统计"最老在队时长" | 一次减法 | 对"worker 慢"敏感（CoDel 思路） |
| ③ 队列深度 | 直接读计数 | ~0 | 只适合"worker 是瓶颈"的场景 |

### 3. 控制环：EWMA + 双水位 + 最短驻留（防止来回抖）

```
每 10ms（每对）：
    arr   = 期间新请求数；done = worker 完成数
    svc   = EWMA(worker 每请求耗时)             // 平滑
    loop  = EWMA(接待循环每批耗时)
    util  = arr * svc                          // Little 定律：利用率估计

    if (loop > T_high) || (util > 0.9) || (queue_depth > 75%):
        关闭一部分连接的 EPOLLIN（或暂停 accept）
    elif (loop < T_low) && (queue_depth < 25%):
        重新打开
```

三个防抖要点：

1. **双水位 + 滞回**（75% / 25%），不要单阈值；
2. **最短驻留时间**（关掉后至少 5~10ms 不再改），否则会高频开关；
3. **EWMA 平滑**（α≈0.2），否则会被突发带跑。

### 4. "信息传递开销"其实可以几乎为 0

- worker 每处理完一个请求就写一次共享计数 ⇒ 会和接待线程的读**抢同一条缓存行**（ping-pong，~50~100ns/次）；
- 改成**每 64 个请求或每 1ms 发布一次**（批量发布），接待线程每 10ms 读一次 ⇒ 摊下来 **<0.3ns/请求**；
- 所以"用信息传递换灵活性"不是必然的代价，**关键是别在热路径上频繁同步**。

### 5. 推荐的背压动作顺序（从轻到重）

1. **停读**（关 EPOLLIN）：让 TCP 窗口反压，最平滑、不丢请求；
2. **限在途**（降低 `ed_store_blocknum`）：对流水线型客户端立竿见影；
3. **暂停 accept**：防止连接堆积把 fd/内存吃光；
4. **显式 503**：仅在配额真正用尽时（阻塞池满、连接超限），并计数告警。

## 五之十八、如果 handler 阻塞了（开发者没走线程池）——实测有多惨

在副本里加一条 `/slow` 路由：handler 里 `usleep(20000)`（阻塞 20ms），其余不变。
用持续慢请求加压，同时量 `/hello` 的端到端延迟：

| 慢请求速率 | 占 worker 池 | **/hello p50** | p90 | max |
|---|---|---|---|---|
| 0 /s | 0% | **0.05 ms** | 0.16 ms | 0.24 ms |
| 50 /s | **50% 的一个 worker** | **20.16 ms（400 倍）** | 20.74 ms | 20.85 ms |
| 100 /s | 100% 两个 worker | 20.14 ms | 20.79 ms | 20.81 ms |
| 200 /s | 200%（过载） | 20.21 ms | 22.24 ms | 27.96 ms |

**结论：只要有一个 20ms 的阻塞 handler，以 50 req/s 的频率出现（仅占池容量 25%），
同一条连接上的普通请求 p50 就从 0.05ms 变成 20ms —— 慢 400 倍。**
机制是 FIFO 任务队列的**队头阻塞**：快请求排在慢任务后面等着。

### 这说明什么

1. **"开发者会记得用线程池"不能作为架构假设** —— 一个人漏一次，整对的延迟就被拖到阻塞时长；
2. **光靠背压也不够**：背压只能把新请求挡在门外，已经在队列里的快请求还是被慢任务挡着（HOL）；
3. 需要三条结构性措施（见下）。

### 三条结构性措施

| 措施 | 做法 | 效果 |
|---|---|---|
| **① 双通道（快/慢队列）** | handler 声明自己属于 fast 或 slow 通道；worker 优先取 fast；slow 任务只在线程池里跑 | 慢任务**永远挡不住**快请求（消除 HOL） |
| **② 自动检测阻塞** | 每个 handler 前后打时间戳；> 2ms 记一条"慢 handler：路由 + 耗时"，dev 模式直接 abort | 把"静默拖慢"变成"可见 + 可定位" |
| **③ 请求 deadline** | 每请求带 deadline；超过（例如 1s）回 408/503 并释放槽位 | 单个卡死请求不会永久占用 worker |

### 另外：你代码里现成的阻塞点

| 位置 | 风险 |
|---|---|
| `ResponseSendMain` 里的 **`sendfile`** | 冷文件（page cache miss）会阻塞——而且它跑在**接待线程**上，比 worker 阻塞更糟（整对全停） |
| `open()` / `stat()`（静态文件路径） | NFS/慢盘可能阻塞 |
| 日志写 tty / 管道 | 满了或终端慢时会阻塞 |
| 未来的 DNS / 数据库调用 | 典型阻塞源 |

⇒ `sendfile` 这条尤其要注意：**它绕过了你的"业务线程"，直接在接待线程上阻塞**。
要么用线程池 + `pread`，要么用 `io_uring`/`RWF_NOWAIT`。

## 五之十九、"不能相信开发者/第三方库"——把目标从"保证不阻塞"改成"阻塞只造成有界损失"

第三方库的阻塞是不可预测的：`getaddrinfo`（DNS 可能等几秒）、TLS 握手、DB 驱动、
`syslog`/tty 写、gzip 大块、NFS 上的 `open()`、甚至大块 `malloc` 触发的缺页。
**你无法审查、也无法约束它们**，所以架构不能建立在"大家都会用异步 API"上。

### 1. 三层防御（都不依赖 handler 自觉）

| 层 | 机制 | 谁执行 | 结果 |
|---|---|---|---|
| **① 每请求硬 deadline** | 接待线程为每个在途请求记录开始时间；超时（如 100ms~1s）→ 直接回 503/408、释放槽位、断开连接 | **接待线程/监督者**（不是 handler） | 客户端立刻拿到明确错误，**不会无限等** |
| **② 卡死 worker 的"牺牲线程"策略** | 同一个 worker 超时超过更大阈值（如 5s）→ 标记为 stuck，**detach 它，另起一个新线程补位**；stuck 数量设上限（如 4） | 监督线程 | 第三方库再烂，也只损失**有界**的容量，不会拖垮整对 |
| **③ 路由自动降级（学习）** | 某路由在窗口内超时 N 次 → 该路由**自动转 slow 池**（下次直接进线程池，不再占用快通道） | 内置统计 | 不需要人标注"哪个 handler 会阻塞"，系统自己学 |

关键点：**deadline 必须由监督者执行**。指望 handler 自己检查时间，对第三方库无效（你把控制权交给了库）。

### 2. 代价（很便宜）

- 快路径：**0 额外开销**（只在每请求记一个时间戳）；
- 触发时：一次错误响应 + 一个线程栈（默认 8MB 虚拟、实际几十 KB）；
- 上限：stuck ≤ 4 ⇒ 最坏损失 4 个线程和它们对应的连接，而不是整进程。

### 3. 第三方库的常见坑（按风险排）

| 风险 | 例子 | 处理 |
|---|---|---|
| ⚠️⚠️ **DNS** | `getaddrinfo` 可阻塞数秒 | 只在池里做；或换带超时的解析器 |
| ⚠️⚠️ **文件** | 冷文件 `sendfile`/`read`、NFS `open()` | 池 / `io_uring` / `RWF_NOWAIT` |
| ⚠️ **TLS** | 握手需要 IO；很多库是阻塞 API | 用异步 TLS 库，或握手进池 |
| ⚠️ **日志** | 写 tty/管道会阻塞 | 无锁队列 + 独立日志线程 |
| ⚠️ **压缩/加密大块** | gzip 1MB 需要毫秒级 | 大块进池，小块内联 |
| ⚠️ **内存** | 大块 `malloc` 触发 mmap/缺页 | 用池（你们已经在做） |

### 4. 一句话

**不要"信任开发者"，要"隔离 + 有界损失 + 自动学习"**：
默认内联（快）、超时即断（明确错误）、卡死即换线程（有界损失）、慢路由自动降级（自我修正）。
这样即使第三方库不可控，系统也只是**部分降级**，而不是整体卡死。

## 五之二十、「弹性业务线程 + 代际交接（CAS）+ 背压」方案评估

### 1. 你的构想（复述）

每组：1 接待线程 + 1 个**运行中**的业务线程 + 若干**休眠**业务线程。
当业务线程运行过久且请求池已满 ⇒ 接待线程发起**非阻塞**的"主业务线程转移申请"；
成功后唤醒一条新业务线程，用 **CAS 交换两者属性**完成交接，旧线程处理完手头任务后休眠；
申请失败或交接后请求池仍满 ⇒ 背压。

**评价：这个方向是对的**，本质是"按需弹性扩容 + 代际交接（epoch/generation handover）+ 背压兜底"。
但实现上有 6 个点必须改对，否则会出现"交接风暴"或数据竞争。

### 2. 必须改对的 6 个点

| # | 问题 | 正确做法 |
|---|---|---|
| 1 | **"CAS 交换两个线程的属性"在 POSIX 线程里不存在** | 交换的不是线程，而是**"谁是这个组的主消费者"**：用一个 `_Atomic uint64_t generation`；旧 worker 记住自己的 gen，发现 `gen != mine` 就退出循环；新 worker 用 `CAS(gen, old, old+1)` 抢到身份 |
| 2 | **交接窗口内会有两个消费者** | 你的单生产者单消费者环在这里不成立 ⇒ 队列必须是 **MPMC**（或交接时用一把很短的锁 / 先生效"旧线程已停取"标志再让新线程开取） |
| 3 | **"运行久"不等于"阻塞"** | CPU 密集型（gzip 20ms）和阻塞看起来一样；触发条件是"**队列满 + 最老在途请求超过 T**"，并且扩容上限按**空闲核数**定（2 核最多加 1~2 条） |
| 4 | **防抖** | 双阈值 + 最短驻留（如 50ms 内不重复交接）+ 空闲 N 秒后回收多余线程（衰减），否则会"扩缩容风暴" |
| 5 | **弹性扩容救不了"卡死的那个请求"** | 它仍然占着槽位与连接 ⇒ 还需要**每请求 deadline**（超时回 503/408）和"卡死线程替换"（detach + 补位，上限 4） |
| 6 | **不能在热路径上 `pthread_create`** | 休眠线程就是"备用线程"；接待线程只做 `sem_post` 唤醒（~2~5 µs，一次性），创建失败（EAGAIN）才走背压 |

### 3. 参考实现骨架

```c
struct Group {
    TaskQueue        *q;            /* MPMC（交接窗口内会有两个消费者） */
    _Atomic uint64_t  gen;          /* 代际：谁是主消费者 */
    _Atomic int64_t   oldest_busy;  /* 最老的在途请求开始时间 */
    _Atomic int       extras;       /* 当前额外线程数 */
    sem_t             spare_sem;    /* 唤醒休眠线程 */
    int               spares;       /* 备用线程数 */
};

void *worker_main(void *arg) {
    Group *g = arg;
    uint64_t mygen = atomic_load(&g->gen);
    for (;;) {
        if (atomic_load(&g->gen) != mygen) break;      /* 被接管 → 让位 */
        Task t;
        if (!q_pop(g->q, &t)) { wait_for_work(g); continue; }
        atomic_store(&g->oldest_busy, now_ns());
        handle(&t);
        atomic_store(&g->oldest_busy, 0);
    }
    back_to_spare(g);                                  /* 休眠，等待下次唤醒 */
    return NULL;
}

/* 接待线程里，非阻塞地判断是否扩容 */
void maybe_scale(Group *g) {
    if (q_len(g->q) < HIGH_WATER) return;
    if (now_ns() - atomic_load(&g->oldest_busy) < T_SLOW) return;
    if (atomic_load(&g->extras) >= MAX_EXTRA) return;   /* 按空闲核数定 */
    uint64_t old = atomic_load(&g->gen);
    if (atomic_compare_exchange_strong(&g->gen, &old, old + 1)) {
        atomic_fetch_add(&g->extras, 1);
        sem_post(&g->spare_sem);                       /* 唤醒一条休眠线程 */
    }
}
```

### 4. 量级与预期

| 动作 | 成本 |
|---|---|
| `CAS` 交接 | ~20 ns（一次性） |
| 唤醒休眠线程 | ~2~5 µs（一次性） |
| 交接窗口内的队列竞争 | 取决于队列实现：MPMC 无锁 ~100 ns/次；加锁 ~1 µs |
| 多一条业务线程的收益 | 仅在**有空闲核**时有效：你 2 vCPU 下接待已占 ~0.8 核，最多再加 1 条业务线程 |

### 5. 结论

- **方向对**：按需弹性 + 代际交接 + 背压，比"固定 1 个 worker"健壮得多；
- **必须把"交换线程属性"改成"代际 CAS + 旧线程让位"**，并把队列改成能容忍短暂双消费者；
- **弹性扩容只解决"吞吐下降"，不解决"单个请求永久卡住"** ⇒ deadline 与卡死替换仍要有；
- 触发条件用"**队列水位 + 最老在途耗时**"，扩容上限按"空闲核数"，并加防抖与衰减回收。

## 五之二十一、「转移式交接（非扩容）+ CAS 自旋」——这个理解是对的

> 你的澄清：不是扩容，只是把"主业务线程"的身份**转移**给另一条线程；两个队列那里用 CAS 自旋一会儿，
> 所以任意时刻仍然只有一个消费者（SPSC 不破）。目的是防"意料之外的阻塞"，不是提吞吐。

### 1. 为什么这样是安全的（关键论证）

- 旧线程阻塞时，它**正卡在 handler 里**，并没有在碰队列的临界区；
- 只要把"检查代际 + 出队"做成一个极短的临界区（`in_cs` 标志或一个 CAS 自旋锁），
  新线程**等这个临界区空出来**再接管 ⇒ **任意时刻只有一个线程在 pop** ⇒ SPSC 仍然成立 ✅；
- 旧线程从 handler 返回后，看到 `gen != mine` ⇒ **不再出队**，做完自己的收尾就回备用池。

所以"CAS 自旋一会儿"是可行的，而且比 MPMC 队列更省（没有第二个消费者带来的缓存行争用）。

### 2. 但要明确它的定位：它买的是"可用性"，不是"吞吐"

| | 效果 |
|---|---|
| ✅ 这一组不再被一个阻塞请求拖死 | 其它连接的延迟回到正常 |
| ❌ 吞吐不会提高 | 仍然只有 1 个活跃 worker |
| ❌ 卡住的那个请求本身不会变快 | 它仍占着旧线程与连接 ⇒ 仍需 deadline |

⇒ 正确的说法是：**把"一对被一个阻塞拖死"变成"只有一个连接受影响"**。
（实测：50/s 的 20ms 阻塞请求就能把 /hello 的 p50 从 0.05ms 拖到 20ms —— 这个机制正是为了解决它。）

### 3. 四个必须处理的细节

| # | 细节 | 做法 |
|---|---|---|
| 1 | **自旋要有界** | 10~50 µs 后放弃本轮（别死等）；失败/超时就走背压，下一轮再试 |
| 2 | **旧线程的收尾契约** | 返回后：不再出队 → 完成/冻结自己的响应（连接可能已被 deadline 关掉）→ 释放自己的请求副本 → 回备用池 |
| 3 | **同连接可能出现两个在途请求** | 旧的卡住 + 新的被新 worker 处理：依赖你现有的 `serial` 发送顺序；确认 `ed_store_blocknum` 槽位够（建议 +1~2） |
| 4 | **卡死线程要有上限** | 否则 100% 阻塞的 handler 会把线程数打爆：`stuck <= K`（如 cores+2），超了直接背压；配合 deadline 回收 |

### 4. 交接协议（伪代码）

```c
/* 全局：gen=当前主线程代际；in_cs=是否有人正在"检查代际+出队" */
static _Atomic uint64_t gen = 1;
static _Atomic int      in_cs = 0;

/* 老线程出队：把"检查代际 + 出队"包进临界区 */
int worker_pop(Group *g, Task *t, uint64_t mygen) {
    if (atomic_load(&g->gen) != mygen) return 0;          /* 快速检查 */
    if (atomic_exchange(&g->in_cs, 1)) return 0;          /* 有人在交接，稍后再试 */
    int ok = 0;
    if (atomic_load(&g->gen) == mygen) ok = q_pop(g->q, t);
    atomic_store(&g->in_cs, 0);
    return ok;
}

/* 新线程接管：CAS 换代 + 有界自旋等临界区空出来 */
uint64_t take_over(Group *g, int spin_us) {
    uint64_t old = atomic_load(&g->gen);
    if (!atomic_compare_exchange_strong(&g->gen, &old, old + 1)) return 0;
    uint64_t mygen = old + 1;
    for (int i = 0; i < spin_us; i++) {                    /* 有界自旋 */
        if (!atomic_load(&g->in_cs)) return mygen;         /* 临界区空了，可以出队 */
        usleep(1);
    }
    return mygen;   /* 即使没等到也没关系：对方下次 pop 会发现 gen 变了 */
}
```

关键点：**换代（CAS）与出队之间用 `in_cs` 隔开**，所以不会出现两个线程同时 pop；
旧线程即使恰好卡在临界区里，最多让新线程等几十微秒。

### 5. 与"扩容"方案的对比

| | 转移式（你的方案） | 扩容式 |
|---|---|---|
| 活跃 worker 数 | **恒为 1** | 2+ |
| 队列模型 | **SPSC**（`in_cs` 保护） | 必须 MPMC |
| 缓存竞争 | 低 | 高（两个 worker 抢同一条队列缓存行） |
| 吞吐 | 不变 | 提高（如果有空闲核） |
| 解决阻塞 | ✅ 转移即可 | ✅ |
| 适用 | 防"意外阻塞"、保可用性 | 需要更多并行度时 |

**结论：用于"防意外阻塞"，转移式比扩容式更合适**——它不引入第二消费者、不增加缓存竞争，
只把"被卡住的那条线程"替换掉；代价是吞吐不涨（这正是你的目标）。

## 五之二十二、"大文件/大对象怎么做到快速分配"

先把两种"大"分开：**大响应（静态文件）** 和 **大请求体**，它们的答案完全不同。

### 1. 大响应（静态文件）：**根本不进内存池**

你现在的代码已经是零拷贝：

```c
/* WebApp.c */  fd = open(path); ResponseFileSet(w, fd, 0);
/* ResponseSendMain.c */
ssize_t sent = sendfile(send_fd, send_ed_fd, &store[next].offset,
                        size_file - store[next].offset);
```

- `sendfile` 直接 **page cache → socket**，应用层**一个字节都不分配**；
- 100MB 视频也是按 offset 分块推，**分配成本恒为 0**；
- 真正的成本在：**磁盘读 / 页缓存命中率**，而不是内存池。

要注意的只有两点：

| 坑 | 处理 |
|---|---|
| **冷文件**（page cache miss）→ `sendfile` 阻塞，而且它跑在**接待线程**上 | 线程池 + `pread`，或 `io_uring`；或 `posix_fadvise(POSIX_FADV_WILLNEED)` 预读 |
| 不要为了"快"把大文件 `mmap` 进进程 | 页表 + 缺页 + `SIGBUS`（文件被截断）都更麻烦，`sendfile` 更省 |

### 2. 大请求体（需要连续缓冲）：**复用比"分配得快"重要**

512KB 的 body 你确实要一块连续内存（解析器要 `strstr`/裸指针）。成本对比：

| 环节 | 量级 |
|---|---|
| 分类链分配（命中空闲链） | **~65 ns**（实测，你现有的 65.5 ns/次） |
| 512KB 的 `memcpy` | **~20~30 µs**（≈20 GB/s） |
| **冷页缺页**（512KB = 128 页，未触碰过） | **~100~250 µs**（每页 1~2 µs） |

⇒ **分配本身从来不是瓶颈，缺页和拷贝才是。** 而分类链天然解决缺页：块被 `free` 后**页仍驻留**，下次分配零缺页。

所以大 body 的做法就是"**把它纳进阶梯，让块被复用**"：

| 尺寸 | 做法 |
|---|---|
| ≤ 128KB | 现有阶梯（已覆盖） |
| 128KB ~ 1MB | **阶梯再往上加几级**（256KB/512KB/1MB），仍然 O(1) + 页复用；大块数量少，每级留 2~4 个块即可 |
| > 1MB | ① 直接 `mmap`/`munmap`（少而大，syscall 可接受）；② 或 spool 到临时文件；③ 或**上限 + 413** |

### 3. 你代码里必须一起改的两处（否则大块白占）

| 位置 | 现在 | 改成 | 原因 |
|---|---|---|---|
| `WorkerThread.c:257` | `allocsize = 4*size + ...` | `size + 元数据` | 4 倍放大让 512KB body 需要 2MB，直接跨进最大类之外 |
| `RspHeaderAlloc` | 每请求固定 **63KB** | 先给 **8~16KB**，不够再增长（响应头通常只有 200~500B） | 63KB 占了你**86% 的分配字节量**（实测直方图），却几乎全是浪费 |

### 4. 一句话

- **静态文件**：不分配（`sendfile`），只要处理好"冷文件不要阻塞接待线程"；
- **大 body**：把阶梯延伸到 1MB 让块复用（免缺页），1MB 以上用 `mmap` 或 413；
- **真正要优化的不是"分配"，而是"别拷贝、别缺页"**：原地解析 + 复用块，比任何分配器技巧都值钱。

## 五之二十三、"小文件能用大文件的页吗"

这句话有两种读法，答案不同。

### 读法 A：小文件能不能也走大文件那套（sendfile + page cache）？

**能，而且你现在就是这么做的**：`SendFile()` 对所有静态文件都是
`open()` → `ResponseFileSet` →（worker 里 `fstat` 取大小）→ `sendfile` → `close`。
也就是说小文件同样走 **page cache**，不占内存池。

但对**小文件**来说，这条路径**反而更慢**，因为它要 4 个 syscall：

| 路径 | syscall | 成本（热） | 成本（冷） |
|---|---|---|---|
| 小文件走 sendfile（现状） | open + fstat + sendfile + close = **4** | ~2~4 µs | **+50~200 µs 磁盘** |
| 小文件预读进内存 + `writev` | **1** | **~0.7 µs** | 0（启动时已读） |

⇒ 业界做法是**按大小分流**：

| 大小 | 走法 | 理由 |
|---|---|---|
| ≤ 64~128KB（html/css/js/ico） | 启动或首访时读进**内存块**（池块或 mmap），命中直接 `writev` | 省 3 个 syscall、免磁盘、免冷启动抖动 |
| > 128KB（10mb.bin、视频） | **`sendfile`**（现状，零拷贝 + offset 续传） | 内存放不下，page cache + sendfile 最省 |

### 读法 B：内存池里能不能让小块复用大块的"页"？

**不能直接复用**：分类链的块是**不可分割**的（512KB 的块不能拆出 2KB 给别的请求）。
真正"跨文件、跨大小共享页"的只有**内核 page cache**（4KB 页，按 inode+offset 索引，全系统共享）——
这跟文件大小无关，小文件一样享受。

如果要在**池内**实现页级共享，就必须回到 **1KB 单位 + 位图/run** 的方案（前面 5.3 节评估过）：

| | 分类链（块不可拆） | 1KB 单元 + 位图 |
|---|---|---|
| 小对象浪费 | 0（精确类） | ≤1KB/块 |
| 大块（63KB） | 独占整块，不浪费 | 需 **63 个连续页**；碎片化时前向爬行 |
| 分配成本 | ~65 ns | 实测 41~135 ns（尺寸相关） |
| 泄漏影响 | 一块 | 一块（1KB） |

⇒ 除非你要"几百字节~几百KB 混在同一条池里并且要求极高利用率"，否则**没必要为了页共享牺牲块级的简单性**。

### 落地建议（针对你现在的静态文件）

1. **启动时预载小文件**：`{path, fd 或 内容指针, 长度, ctype}` 表；
2. 小文件命中 → `ResponseHeaderSet("Content-Length", n)` + 长度版 body API（**注意：现在的 `ResponseBodySet` 用 `strlen`，二进制/favicon 会被截断**）；
3. 大文件保持 `sendfile` + offset 续传（你已有 EAGAIN/半包处理）；
4. 阈值做成配置（默认 64KB）；
5. 缓存只读、启动后不可变 ⇒ 多对之间**不需要锁**（要更极致就每对一份，几百 KB 而已）。

## 五之二十四、"小请求能不能用大请求的块？小请求为主时大块怎么办？"

### 1. 实测：小请求为主时，大块**根本不占内存**

只发 96~448B 的请求（200 万次，在途 2000）：

```
峰值活跃 = 540 KB
arena 已切 = 713 KB（配额 64 MB）
在用 = 568 KB   利用率 = 79.6%
有 chunk 的类：[112B][144B][192B][240B][304B][384B][480B]   ← 只有这 7 个类存在
```

⇒ **63KB / 512KB 那些类占用 0 字节**，因为实现是"**按需切 chunk**"：
没有任何"按比例预分"，某个类没人用就永远不占内存。

唯一的固定开销是**每个用到的类一块 16KB 地板**（7 类 ≈ 112KB）；
把 `chunkMin` 从 16KB 降到 4KB，这个测试的利用率能从 79.6% 提到 ~90%（代价是 chunk 数量变多）。

### 2. 大块什么时候会"白占"

只有当**大请求出现过一波、之后长期不来**时：那批 chunk 会留在该类的空闲链里（不会泄漏，但也不还）。

三条改进（按代价从小到大）：

| 改进 | 做法 | 代价 | 效果 |
|---|---|---|---|
| **A. 借块（borrow）** | 本类空时，向上借一个"块大小 ≤ 2× 请求"的块 | 一个 ≤3 次的小循环 | 小请求能吃到上级类的空闲块；利用率↑ |
| **B. chunk 整块归还/改挂** | 每 chunk 一条子空闲链 + `liveCount`；归零时退回 arena 或改挂给别的类 | ~40 行 + 每 chunk 一个计数 | 长期不用的大块真正释放 |
| **C. 拆块** | 大块切成小单元（1KB 单元 + 位图） | 块不再等大 ⇒ 需要扫描 | 利用率最高，但 63KB 需 63 个连续页 |

### 3. 借块为什么是安全的（关键技巧）

`free(ptr)` 是靠**指针落在哪个 chunk** 来定位类的 ⇒ 借出去的块，释放时会自动回到**它所属的 chunk（原类）**，
**不需要给每个块加尺寸头**，也不会造成"跨类混放"的碎片累积：

```
2KB 请求 → 2KB 类空 → 向 4KB 类借一块
free(ptr) → chunk_of(ptr) = 4KB 类的 chunk → 挂回 4KB 类的空闲链  ✔
```

要做的只有：限制"最多借几级 / 最多浪费几倍"（例如只借相邻一级、块 ≤ 2× 请求），
并统计"借块率"，避免为了省几个字节把内部浪费放大。

### 4. 结论

- **小请求为主时不需要担心大块**：按需切 chunk ⇒ 大块类占 0；
- 真要让"大块的空闲容量"给小请求用：**借块**（A）最划算，且实现安全；
- 想要"任意尺寸共用同一段内存"：那才需要 1KB 单元 + 位图（C），代价是扫描与大块连续性问题。

## 五之二十五、尺寸跨 32B ~ 几 MB 时怎么办：分层（tiered）分配

> 跨 5 个数量级不可能用"一种机制"同时最优。业界统一答案是**分层**，每层用最合适的机制。

### 1. 推荐的三层

| 层 | 尺寸 | 机制 | 内部浪费 | 备注 |
|---|---|---|---|---|
| **T1 小对象** | 32B ~ 16KB | **1.25× 阶梯类 + 每类 chunk**（货架式） | ≤20%，命中精确尺寸 = 0 | 已有实现，热路径 ~65ns |
| **T2 中对象** | 16KB ~ 1MB | 同一阶梯继续（类更粗：1.5× 或 2×），chunk = 1~2 个块 | ≤33~50% | 数量少；块空闲时要能**整 chunk 归还** |
| **T3 大对象** | > 1MB | **直接 `malloc`/`free`**（glibc 对大块本身就是 mmap/munmap） | ≤4KB（页粒度） | `free` 自动还系统；不用池 |

### 2. 为什么大对象反而"不用池"

- `>1MB` 时，**浪费按页算**（≤4KB）比"类"的百分比浪费小得多（1MB 的 20% = 200KB ≫ 4KB）；
- glibc 对 >128KB 的 `malloc` 就是 `mmap`，`free` 就是 `munmap` ⇒ **代码量 0、内存自动归还**；
- 大对象的成本大头是**拷贝与缺页**（512KB≈25µs 拷贝、冷页 128 次 ≈100~250µs），不是"分配算法"；
- 若大对象**高频且尺寸重复**（比如固定 2MB 的缓存块），再给它一个 2MB 类做复用，省掉每次 mmap/munmap。

### 3. 类数不是问题

1.25× 从 32B 到 1MB：`log(32768)/log(1.25) ≈ 46` 类；到 8MB 约 60 类。
每个类元数据 ~40B ⇒ **总共 ~2.4KB**，可以忽略。
所以"单一阶梯一路到 1MB"在**元数据上完全可行**，真正的差别在**大块的跨尺寸复用**：

| 路线 | 优点 | 缺点 |
|---|---|---|
| **单一阶梯到 1MB + chunk 归还** | 实现简单、碎片 ≤20% | 大块不能拆给小请求（尺寸结构变了会闲置，靠"整 chunk 归还"缓解） |
| **T1 细分 + T2 粗分 + T3 mmap** | 各层最优、T3 自动归还 | 三套阈值/统计，代码多一点 |

### 4. 落地建议（从现有实现出发，改动很小）

1. `CLASS_POOL_BLK_MAX` 从 128KB → **1MB**，`CLASS_POOL_MAX_CLASS` 40 → **64**（阶梯自动生成）；
2. 给 chunk 加 `liveCount` + 每 chunk 子空闲链 ⇒ **chunk 空时整块归还**（约 40 行）；
3. `ClassMemoryPoolAlloc` 里加一条：`needSize > 1MB` ⇒ 转 `malloc`，并返回一个标记（或提供 `ClassMemoryPoolAllocHuge`），`free` 侧用 `free()`（需在调用点区分，或用本池的一个小包裹函数）；
4. 用**真实直方图**调阶梯：把最频繁的几种尺寸加成"精确类"（你现在是 1KB/2KB/6KB/63KB，正好都在边界上）。

### 5. 一张图记住

```
32B ────── 16KB ────────── 1MB ──────────── 几 MB
 └ 1.25× 类 + chunk ┘   └ 粗类/整 chunk 归  ┘  └ malloc/mmap ┘
    （热、要快、要零浪费）   （少、要能还）        （页粒度、自动还）
```

**一句话**：小对象靠"细分 + 货架"，中等靠"粗分 + 整块归还"，大对象**根本不该进池**（mmap/malloc 就是最好的大对象分配器）。

## 八、一句话总结

**搭便车这件事你写对了**：功能全过、404 路径也回收、valgrind 0 泄漏、RSS 平稳、延迟仍是 0.03ms。

### 9.1 基线（可复现）

| 指标 | 值 |
|---|---|
| 每请求 CPU | **19 µs**（接待 14.7 + worker 2×2.2） |
| 每请求 syscall | **7 次**：1.87 futex / 2.06 read / 2.01 write / 1.02 epoll_ctl |

### 9.2 五个步骤（每步都能独立验收）

| 步 | 改什么 | 每请求省 | 验收 |
|---|---|---|---|
| **1** | 去掉每响应的 `epoll_ctl(MOD)`：边沿触发，只在 `EAGAIN` 时才关注写事件 | ~1 syscall（1~2 µs） | 27 项功能 + 流水线 2×60/8×20 |

| **3** | 读到 `EAGAIN` 就退出（去掉多余的那次 read） | ~1 syscall | 分片 POST、keep-alive |
| **4** | 队列：每对一条 SPSC + 批量通知（一次唤醒取多个任务） | ~1.87 futex → ~0.2 | c=50~400 延迟与吞吐 |
| **5** | 每对（接待+worker）独立 + 每对 listen（`SO_REUSEPORT`） | ×核数 | 多核机器压测（本机测不出） |

**保守预期**：1~4 步后 **19 µs → 8~10 µs**（单核 10~12 万），第 5 步再 ×N。

### 9.3 重构期间不能破坏的不变量

1. **每连接 `serial` 顺序**与 `pack_in_path < ed_store_blocknum` 的流控；
2. **请求副本所有权**：谁分配谁释放（现在是接待线程，靠 `httpNeedFree` 搭便车）——多对之后仍然如此；
3. **`sendfile` 的 `offset` 续传**（EAGAIN 后从断点继续，不能重发已发部分）；
4. **定时器语义**（`TimerReset` 在收发两侧的刷新时机）；
5. **`FdTableFind` 与关闭路径**：`fd_ob==NULL` 分支现在会漏 `httpNeedFree`（见 §6 的 P1）。

| `ReceiverThread.c:32,33`、`WorkerThread.c:82,83` | `2024*1024` 不是 2 的幂 ⇒ 池初始化失败 ⇒ **首个请求 SIGSEGV** | 改成 `2048*1024` |

## 十、关于"请求 ≤1MB、响应（非文件）≤64KB、比例 16:1"的评估

### 1. 两个"上限"合理，"16:1 硬比例"不建议

| 你的设定 | 评价 |
|---|---|
| 请求 ≤ **1MB** | ✅ 合理（再大就 413；也避免 `4*size` 把分析块撑到 4MB） |
| 非文件响应 ≤ **64KB** | ✅ 作为默认策略合理（头部本来就只有几百字节） |
| **16:1 的固定比例** | ❌ 不建议：合法的"小请求、大响应"场景会立刻撞线（JSON、HTML、模板渲染、`/api/echo` 回显 1MB body） |

**比例耦合没有收益**：两个上限各自独立反而更灵活；用比例反而把"响应上限"绑死在"请求上限/16"上。

### 2. 建议的替代规则（四条）

1. **各自独立上限**：`request ≤ 1MB`、`非文件响应 ≤ 64KB~1MB`（按业务定）；
2. **超限策略要区分**：请求超限 → **413**（读之前就用 `Content-Length`/累计字节判断，别先读进内存再拒绝）；
   响应超限 → **不要截断**，要么提高上限，要么改**流式/临时文件**（`/api/echo` 这种回显就属于必须流式或限长的）；
3. **内存预算**：`每连接在途字节 ≤ request_max + response_max × 流水线深度`，用它来定 `ed_store_blocknum`；
4. **常用路径要小**：头部/响应块**默认 8~16KB**，真的写满再增长到 64KB（见第 3 点）。

### 3. 比"比例"更值钱的一件事：把 63KB 头块改小

实测直方图：**63KB 头块占 86% 的分配字节量**，但实际头部只有 200~500B。

| 方案 | 每请求分配 | c=200 时（典型） |
|---|---|---|
| 现在：固定 63KB | 63KB | ~12.6MB |
| **改成 8~16KB（写满再增长到 64KB）** | 8~16KB | **~1.6~3.2MB** |

收益：池子footprint 直接降 4~8 倍；而且 64KB 的"上限"照样能满足（增长路径）。

### 4. 内存账（c=200）

| 场景 | 每请求 | 合计 |
|---|---|---|
| 典型（/hello：1KB 分析 + 8KB 响应 + 6KB 指针 + 2KB 判定） | ~17KB | **~3.4MB** |
| 最坏（每连接 1MB body 在途 + 64KB 响应） | ~1.07MB | **~214MB** ✗ 不能预分配 |

⇒ 大请求必须**按需**分配（分类链的 chunk 惰性切分 / 或 >256KB 走 `mmap`），不能按"最坏 × 连接数"预留。
