## 1. 待办 1：内存池

### 1.1 现在的问题

1. **请求 >32KB 必 503**（详细推导见 `CODE_AUDIT_FINDINGS.md` 第 3 节）：
   `ReceiverThreadInit` 里 `MemoryPoolInit(&store_area,10,6,500,400)` —— 10 个尺寸类（1KB~512KB），但 `init_max=6` 只给前 6 类（1KB~32KB）预分配 400 条，**64KB/128KB/256KB/512KB 四类都是 0 条**；而 `MemoryPoolAlloc` 是非扩容的 ⇒ 暂存区扩到 33KB 时落进 64KB 类 ⇒ `notfull=0` ⇒ `FdClose(503)`。
2. **`MAX_BODY_SIZE` 写的是 1MB，实际可用 ≈32KB**（文档与实现不一致）。
3. **跨线程释放不安全**：`MemoryPoolFree`/`MemoryEntryFree` 里 `haded_num--` 不在锁内（`MMemoryStackPush` 虽然有锁）；目前靠"内存只由属主线程归还"绕开 —— **这个约束是对的，要坚持**（新池无锁，见 1.3）；现在唯一违反它的是 `WorkerThread.c:262`，解决办法见**第 7 节（搭车回传）**。

### 1.2 新内存池落地时建议满足的"接口 check-list"

| 要求 | 原因 |
|---|---|
| 按尺寸类分配 + `notfull` 降级语义保持不变 | 上层 `503` 降级逻辑不用改 |
| ~~**允许任意线程 `free`**~~ **（❌ 已否决）** | 新池 `CWebMemoryPool` 是**无锁 + 线程私有**（见 1.3）⇒ 跨线程 free 会数据竞争。改为"\*\*搭车回传、属主线程 free\*\*"（第 7 节），池保持完全无锁 |
| 大尺寸类**可扩容**（或至少 64KB~1MB 有配额） | 否则 >32KB 的请求永远 503；顺带让 `MAX_BODY_SIZE=1MB` 名副其实 |
| `alloc/free` 要有"是否来自本池"的判定（已有） | 避免把 malloc 兜底块误按池块归还 |
| 最好能提供 `pool_free_any_thread(pool, ptr, size)` 这类显式接口 | 语义清晰，便于 code review |

> 提醒：扩容语义要小心"扩容时移动了内存、而旧指针还在别处使用"的悬垂问题（你们历史上踩过），所以"扩容"只对**暂存区这种单属主、可安全搬迁**的对象开放更稳。

### 1.3 新池 `CWebMemoryPool` 评估（已读源码 `~/c_code/CWebMemoryPool`）

**设计**：一整块连续内存切成 `entryNum` 个 `perSize` 子池 → 子池内 **bump 追加**（每块 `needSize + 4`，尾部 4B 护栏）→ **只有该子池"在用计数归零"时才整池复位**；**全程无锁**，`MemoryPoolFree(p, ptr)` 只需要指针。

**优点（相对老池）**：

| 项 | 结论 |
|---|---|
| 结构 | 115 行、无元数据节点、`alloc` 基本是"指针加法"，缓存/内存都友好（相邻块 100% 连续） |
| 内存效率 | 每块只付 4B 护栏（老池最小条 1KB、malloc 头 24~32B）；实测"1000 块 64B：1024B/块 → 68B/块" |
| 速度 | 你们实测：c_web 真实形态（63KB 头 + 70KB 打包 + 4×1KB）**0.031 µs/请求**，老池 0.077 µs ⇒ 约 2.5 倍 |
| 碎片 | 整池复位，不存在空闲栈高水位；200 轮申请/全还后地址稳定 |
| 工程化 | 84 断言 + 影子模型 8 条不变式 + ASAN/UBSAN/TSAN + 与老池/malloc 同进程对比（PERF_REPORT / TEST_REPORT） |

**对 c_web 的三条硬约束（按风险排序）**：

1. 🔴 **必须线程私有**（池无锁）⇒ 换池前必须消灭那处跨线程 free ⇒ **待办 4**；
2. 🔴 **漏 1 块 = 永久丢一整个子池**（`hadAllocNum` 永不归零）⇒ 既有泄漏路径必须先堵（`tempPack` 覆盖、`FdClose` 早退）⇒ **待办 3**；
3. 🟠 **要求"请求内整批释放"**：一个子池的块来自多个请求，谁没还完整池都回收不了。你们 README 第 9 条实测：随机交错释放 ⇒ **降级 27.7%~33.3%**；整请求一起释放 ⇒ **0 降级**。

**代码层细节（换池时一起处理）**：

| 细节 | 影响 |
|---|---|
| 每块只保证 **1 字节对齐**（步长 `needSize+4`） | c_web 的 `RspHeaderAlloc` 把池内存当 `Response_Header_Entry*` 用（含 `char*` 成员）→ 现在可能非对齐 ⇒ UB（x86 能跑、ARM 可能崩）。建议步长向上取整到 8/16，或上层改 `memcpy` |
| **-O0 下扫描成本放大** | 你们基准是 -O2；c_web 是 -O0，`for(i<entryNum)` 扫描 + `gapSize/perSize` 除法都是"真循环/真除法"（PERF_REPORT 自己也测了：256 个残量池 → 118~208ns）。建议配合 hint/位图/移位补丁，或 c_web 编到 -O1+ |
| **`perSize` 决定单块上限** | 上限 = `perSize - 4`，超了直接 `notfull=0`（老池 >64KB 会 malloc 兜底、永不失败）⇒ `MAX_BODY_SIZE=1MB` 要真支持，`perSize` 必须 ≥1MB+4 |
| **`RspHeaderAlloc` 固定借 63KB/请求** | 一大半子池被头块独占、`perSize` 被迫 ≥64KB。建议把头块改成按需大小（2~8KB 起、不够再扩） |
| `free` 不再要 size、不校验重复释放、无 `Destroy`、`int` 容量、无 include guard | 13 处调用点要改（`(x/1024+1)*1024` 那套 KB 取整可删）；"双 free"会静默把子池提前复位（两个在用请求共用内存）⇒ 必须靠调用方纪律 |

### 1.4 换池的前置条件（顺序不能反）

1. **待办 4**（跨线程 free → 搭车解决）—— 否则新池直接数据竞争；
2. **待办 3**（`tempPack` 多槽 + 序号后移 + 关闭清理）—— 否则漏 1 块丢 1 池；
3. **释放节奏改成"请求级整批"**（把 `headers`/`body` 的释放推到发送完成，与 `packed` 块同批还）—— 否则 27~33% 降级；
4. 最后才换池，并按"**单请求最大用量**"给每个池配 `perSize`（让一个请求≈独占一个子池 ⇒ 0 降级、无残量池扫描）。

## 2. 待办 2：400 并发死锁 —— 解决方案

### 2.1 先把"环"再画一次（决定方案的关键）

```
   业务线程 ──投递响应(阻塞 sem_wait)──► 收发线程的 Thing_queue(100)   满 ⇒ 业务线程等
        ▲                                                              │
        └── 等收发线程排空 Thing_queue ◄───────────────────────────────┘

   收发线程 ──归还响应内存(阻塞 sem_wait)──► 业务线程的 memory_queue(100) 满 ⇒ 收发线程等
        ▲                                                              │
        └── 等业务线程排空 memory_queue ◄──────────────────────────────┘
```

**只要"两条投递都还会阻塞"，环就必然存在**（把队列放大只是降低概率）。所以目标很明确：
> **让"投递"永不阻塞；收不下的东西暂存在本地，稍后重试。**

### 2.2 你的思路：仿照任务队列的做法 —— 正确，而且这条边本来就已经是这么做的

看现在的任务队列（收发 → 业务），它**已经**是这个模式：

| 环节 | 现在的做法 | 代码 |
|---|---|---|
| 投递失败不阻塞 | `TasKQueuePush` 满了**直接 `return 0`** | `Queue/TaskQueue/TaskQueue.c:43-46` |
| 失败的内容暂存 | `ReceiverToWorker` 把它塞进 `tempPack` | `Threads/ReceiverThread.c:48-56` |
| 稍后重试 | 收发线程每轮循环顶部重试一次 `tempPack` | `Threads/ReceiverThread.c:77-81` |

**所以"仿照它"就是把另外两条阻塞边改造成同一模式**；而剩下的问题（`tempPack` 只有 1 槽、会覆盖）正好是第 3 个待办，一并解决。

### 2.3 具体设计（两条边分别怎么做）

#### 边 A：业务线程 → 收发线程的 `Thing_queue`

```c
/* 1) 投递改成非阻塞（只在这一处改语义） */
int ReceiverQueuePush(...){
    if(sem_trywait(&sq->sem_thing_queue_notfull) != 0) return 0;   /* 满：不阻塞，交给调用方 */
    pthread_mutex_lock(&sq->mutex_thing);
    ... 原有入队 ...
    pthread_mutex_unlock(&sq->mutex_thing);
    return 1;
}

/* 2) 业务线程：投递失败就挂到自己的"待投递链"（不阻塞、不覆盖） */
if(ReceiverQueuePush(W->Thing_queue, ...) != 1){
    PendPush(&profes->out_pend, entry);     /* 小链表节点，~40B/条 */
}

/* 3) 重试点：每个任务开始前 + 空闲等待循环里（与 CleanMemoryQueue 同一位置） */
void WorkerPendFlush(Worker_Thread* profes){
    while(!PendEmpty(&profes->out_pend)){
        if(ReceiverQueuePush(..., PendFront(&profes->out_pend)) != 1) break;  /* 还是满，下次再来 */
        PendPop(&profes->out_pend);
    }
}

/* 4) 背压：待投递链超过上限时，本 worker 先不要再取新任务（仿 RequestComeMain 的 pack_in_path 逻辑） */
if(PendCount(&profes->out_pend) >= OUT_PEND_MAX) { /* 回到等待，不去 pop 新任务 */ }
```

**为什么这样安全（两个关键点）**：
1. **顺序不受影响**：`Thing_queue` 里的条目带 `serial`，接收线程是按 `serial % blocknum` 放进发送槽的（`ResponseSendMain.c:5` `FdNextSendPut`），所以**到达顺序无关**；迟到的响应会自己落到自己的槽位 ✓
2. **不会误判"发完了"**：接收线程的 `ser_nex_send` 只在槽位 `use==1` 时才前进（`ResponseSendMain.c:95` `while(store[next].use==1)`），所以缺了某个序号它会**停在原地等**，不会跳过 ✓（代价：这条连接后续响应会被 HOL 住，所以"暂存的必须最终一定投出去"——重试点要足够频繁：每任务一次 + 空闲循环一次）

#### 边 B：收发线程 → 业务线程的 `memory_queue`（归还响应内存）

```c
/* 1) 同样改成非阻塞 */
int WorkerQueuePush(...){
    if(sem_trywait(&sq->queue_notfull) != 0) return 0;
    ... 原有入队 ...
    return 1;
}

/* 2) 收发线程：归还失败就挂到自己的"待归还链"（条目自带属主 queue 指针，晚点还也安全） */
if(WorkerQueuePush(m, size, ptr) != 1) PendPush(&w->free_pend, {m, size, ptr});

/* 3) 重试点：收发线程每轮内层循环顶部（本来就在那里跑发送泵） */
ReceiverPendFlush(w);   /* 非阻塞地尽量还，还不下就留着 */
```

**边界情况**：
- 待归还链会不会无限长？**不会**：每条对应一块已分配的内存，数量受内存池总量约束；池满时上层本来就会 503 ✓（也就是说"链表长度"天然有界）
- 会不会丢内存？不会——条目还在链表里，最终会被归还；进程退出时的残留可忽略 ✓
- 内存多久才还回去？最坏等到该 worker 有空排空 `memory_queue` 的瞬间（几 ms 级），期间池里少几块 → 有轻微 503 风险，但**不再死锁** ✓

#### 这样"环"为什么就断了（资源依赖图）

```
改之前：业务线程持有"待投递响应" → 等 Thing_queue 空位（由收发线程释放）
        收发线程持有"待归还内存"   → 等 memory_queue 空位（由业务线程释放）   ← 成环
改之后：两边"待投递/待归还"都变成【自己本地的链表，不需要对方配合就能继续往下走】
        ⇒ 不存在"持有并等待对方释放"的边 ⇒ 结构上不可能死锁 ✓
```

### 2.4 方案 B（❌ 已作废）：把 `memory_queue` 整条边删掉

> **作废原因**：新池 `CWebMemoryPool` **全程无锁、必须线程私有**（见 1.3 节）⇒ "收发线程直接 free 到属主池"会数据竞争。
> 这条边改用「**无锁 SPSC 队列**」（第 8 节）；"跨线程 free" 改为「**搭车回传**」（第 7 节）。下面保留原设想仅供对照。

既然新内存池要做成**线程安全**的（见第 1.2 节 check-list），那就可以让**收发线程直接 `free` 到属主池**，不再经过"worker 的 memory_queue"：

```c
/* 响应槽里存的不再是 Worker_Queue*，而是属主 Memory_Pool* */
MemoryPoolFree(owner_txt_pool, ptr, (size/1024+1)*1024);   /* 任意线程都可调用 */
```

收益：
- **死锁少一条边**（连"暂存 + 重试"都不需要了，归还这条路永不阻塞）；
- 少一次跨线程交接（更快，且 worker 不必为了回收内存而被唤醒）；
- 内存回收更及时（发送完就在收发线程里还掉）⇒ 高并发下 503 更少。

代价：新池必须保证 `free` 的**计数与空闲栈线程安全**（现在 `haded_num--` 不在锁里，跨线程会错账）。

### 2.5 方案 C（可选加固）：让 `Thing_queue` 永不拒绝

把 `ReceiverQueue` 从"100 槽固定环 + 信号量"改成**动态环 / 链表（不设硬上限）**：
- 条目很小（~64B），1000 条也才 64KB；
- 真正的上限交给"在途限制"（每连接 `pack_in_path>=100` 就不再读）和内存池容量；
- 好处：连"暂存 + 重试"都省了，直接 `return 1` 就完事。

### 2.6 方案 D（保底，强烈建议无论选哪个都加上）：`sem_timedwait` + 降级

把剩下所有"可能无限等"的 `sem_wait` 统一换成 `sem_timedwait`（比如 5~50ms）：
- 超时后**明确降级**（丢弃这个响应 / 把归还延后 / 关闭该连接并回 503），而不是继续等；
- 这样即使某个边界情况没考虑到，也**不会永久卡死**（最坏是这一次请求失败），进程永远保持可用。

### 2.7 推荐组合与落地顺序

| 阶段 | 做什么 | 解决 |
|---|---|---|
| ① | 先换**线程安全的新内存池**（第 1.2 节 check-list） | 待办 1 |
| ② | ~~方案 **B**~~（❌ 作废：新池线程私有）→ 改用第 8 节的**无锁 SPSC 队列** | 死锁少一条边 |
| ③ | 方案 **A**：`Thing_queue` 投递改 `sem_trywait` + worker 本地待投递链（+ 上限背压） | 死锁另一条边 |
| ④ | 方案 **D**：所有残留 `sem_wait` 改 `sem_timedwait` + 降级 | 保底"永不永久卡死" |
| ⑤ | 待办 3：`tempPack` 多槽 + 序号后移（见第 3 节） | 丢请求/串号卡死 |

> 只做 ③ 也能打破环（因为环需要两条边都在等），但 ② 更省事、更快；④ 是保险丝。**建议 ②③④ 一起做**（改动集中在 `ReceiverQueue.c`、`WorkerQueue.c`、`ReceiverThread.c`、`WorkerThread.c` 四处）。

### 2.8 风险与代价（实话实说）

| 方案 | 收益 | 代价/风险 |
|---|---|---|
| A（非阻塞 + 本地暂存） | 直接破环；不需要动内存池 | 多一个链表与"上限背压"逻辑；延迟投递会让该连接短暂 HOL（几 ms）；必须保证重试可靠，否则响应会一直不发出 |

| C（Thing_queue 不限长） | 最简单 | 内存峰值上升（仍受在途/池容量约束）；队列长度失去显式上限，压测时要看 RSS |
| D（超时降级） | 永远不会永久卡死 | 超时那一次请求会失败（503/丢响应），要选好"降级动作" |

## 3. 待办 3：接待线程"投递失败后剩下的包"怎么管

### 3.1 现状（三段代码，三个后果）

```c
/* ① 业务线程投递请求失败 → 塞进唯一那个槽 */
int ReceiverToWorker(...){
    int e0=TasKQueuePush(taskQueue,w,fd,serial,error_reason,h,h_size);
    if(e0!=1){ TempPackPut(w->tempPack,true,fd,h,h_size,error_reason,serial); return 0; }  /* 不检查 had！*/
    return 1;
}
/* ② 唯一的重试点 */
if(w->tempPack->had==true){ int put=ReceiverToWorker(...); if(put==1) TempPackPut(...,false,...); }

/* ③ 序号在投递之前就被消费 */
fd_ob->ser_fina_send++;
int put = ReceiverToWorker(...);
if(put != 1) break;
```

| 后果 | 机制 |
|---|---|
| **丢请求** | 槽里已经有一个（`had==true`）时，新失败会**覆盖**它 → 被覆盖的请求永远不会被执行、也不回响应 |
| **漏内存** | 被覆盖的请求占着接收线程 `http_pool` 的请求副本块，没人释放 |
| **整条连接卡死** | ③ 里序号已被消费，但请求丢了 → 接收线程按 `serial` 顺序等这个永不出现的响应（`while(store[next].use==1)`）→ 该连接后面所有响应都发不出去，直到 60s 超时 |

> 实测表现：多连接同时一次性发很多请求时（如 2 连接×60 深度），偶发丢 2%~15% 响应、连接假死；服务端日志用探针能抓到 `TEMPPACK_OVERWRITE`。

### 3.2 它和"死锁"是同一类问题

三个待办里，**2 和 3 都是"跨线程投递失败后怎么办"**：
- 死锁：失败时**阻塞**（把对方也拖死）；
- 剩包：失败时**覆盖/丢弃**（丢数据、漏内存、串号）。

⇒ 可以用**同一套"非阻塞 + 本地暂存 + 定期重试 + 有界背压"**的基础设施统一处理（一个 `pend_list` 结构体复用到三处）。

### 3.3 设计

| 项 | 现在 | 改法 |
|---|---|---|
| 容量 | 1 槽 | 小环形队列（如 16~64）或链表（自然有界） |
| 覆盖 | 无条件覆盖 | **入队前检查**；只有队列满时才进入"背压"（暂停读该连接 / 暂停 pop 新任务），绝不覆盖 |
| 序号 | 投递前 `ser_fina_send++` | **投递成功后再 ++**（或失败时回滚），保证"序号被消费"和"请求真的被接受"原子 |
| 连接中途关闭 | 残留请求块泄漏 | `FdClose` 时把该 fd 在暂存里的条目清理掉（`MemoryPoolFree(http_pool, h, (h_size/1024+1)*1024)`），或直接放弃并计数 |
| 重试点 | 每轮一次（单槽） | 每轮把暂存**尽量排空**（while 循环直到投递失败为止） |
| 可观测性 | 无 | 加计数：暂存条目数、flush 次数、被覆盖/丢弃次数（压测时直接看） |

### 3.4 验证

流水线压测（`2 连接×60`、`8 连接×25`、`1 连接×500`）各 **20 轮**，判据：
- 每轮"拿回响应数 == 发出请求数"、结束方式都是"全部读完（连接保持）"；
- 服务端 `被覆盖/丢弃` 计数为 0；
- valgrind 的 `definitely lost` 仍为 0。

## 6. 结论（一句话）

- **死锁**：你的思路（仿任务队列）完全正确——把"两条阻塞投递"改成"**非阻塞 + 本地暂存/无锁队列 + 定期重试**"，环就断了。具体到你的新池（**无锁、线程私有**）：边 1 用"**请求副本搭车回传、收发线程 free**"（第 7 节），边 2 用"**每个 worker 一条无锁 SPSC 队列**"（第 8 节），再加"`sem_timedwait` 超时降级"做保险丝，做到**结构上不可能永久卡死**。
- **剩包**：同一个模式 + 多槽暂存 + 序号后移，就能同时消除"丢请求/漏内存/串号卡死"。
- **内存池**：**不要**去改成"跨线程可 free"（新池是无锁的，改了就是数据竞争）；正确做法是**让每块内存都由属主线程释放**（请求副本搭车、响应缓冲走无锁队列），池才能保持完全无锁。换池前先补齐第 9 节的 1~3 步。
- **容量依据（你提的）**：释放包与响应块 **1:1 对应** ⇒ 队列长度天然有界（≤ 池容量/最小块，实际 ≈ 在途响应数，400 并发约 3.2KB）；但"有界 ≠ 健康"——它变长的代价是池的有效容量下降 ⇒ 及时排空 + 堵住四个"破坏 1:1"的漏点（第 8.3 / 8.4 节）。

## 7. 待办 4（定稿）：跨线程 free —— 用"搭车"解决，池子保持无锁

### 7.1 问题

```
Threads/WorkerThread.c:262   MemoryPoolFree(w->http_pool, ptr, 1024*(size/1024+1));
                              ↑ 业务线程在 free 收发线程的池（w 是 Receiver_Thread*）
```
请求副本由收发线程在 `RequestComeMain.c:63` 从 `Receiver_Thread->http_pool` 分配；老池每档有空闲栈 mutex 所以"侥幸安全"，**新池无锁 ⇒ 数据竞争**（与收发线程的分配并发冲突）。

### 7.2 方案（你的思路）：free 只由属主线程做，指针搭车回传

```
业务线程 ──响应包(Thing_queue 条目)──► 收发线程
            包里新增一个字段： char* free_req;   ← 就是请求副本指针
收发线程 pop 到这个包时，用自己的 http_pool free 掉它
```

**为什么这是最省的解法**：
- 响应包本来就要回传给收发线程（`ReceiverQueuePush` 已有通道）⇒ **不新增队列、不新增唤醒、不新增信号量、不加锁**；
- 新池 `MemoryPoolFree(p, ptr)` **只要指针**（不要 size）⇒ 包里加一个 `char*` 就够；
- free 全部发生在**属主线程** ⇒ 新池可以保持完全无锁 ✓

### 7.3 落地要点（前两条最容易漏）

1. **错误响应分支也要带**：`WorkerMain` 的错误分支（`WorkerThread.c:186`）是硬编码 `NULL` 的那条；只改正常分支（`:194`）会漏掉所有 404/405/503 路径 ⇒ 那些请求副本会漏还 ⇒ 新池下**每个漏块永久占死一整个子池**。
2. **接收端"pop 即 free"**：在 `GetAndJudge`（`ResponseSendMain.c:27`）拿到 `Receiver_Queue_Entry` 后**立刻** free，位置要在"`fd_ob==NULL` / `FdClose` / 正常发送"所有分支**之前** ⇒ 任何路径都不可能忘。
3. **响应若被丢弃，搭车指针必须一起 free**：这条把待办 4 和待办 3 绑在一起 —— "不覆盖、不丢弃"必须先做到。
4. **生命周期变长**：请求副本从"解析完立刻还"变成"响应被 pop 时才还" ⇒ `http_pool` 容量要按"**在途请求数 × 单请求副本**"配。
5. **字段落点**：`Response` 加 `char* free_req;`（业务侧暂存）→ `Receiver_Queue_Entry` 加同名/同义字段 → `ReceiverQueuePush` 加一个参数（注意它已有 11 个参数，别插错位置）。

### 7.4 边界

- ✅ 解决：换池的**最大阻塞项**（线程安全）消失；全代码再无跨线程池操作。
- ❌ 不解决：死锁的另一条边（`memory_queue` 归还响应缓冲仍是阻塞投递）⇒ 见第 8 节。

## 8. 待办 5（定稿）：`memory_queue` 改成无锁 SPSC 队列

### 8.1 现状

`memory_queue`：固定 100 槽环 + `sem_wait(&queue_notfull)`（`Queue/WorkerQueue/WorkerQueue.c:30`）⇒ **满了就阻塞** ⇒ 死锁的一条边。
为什么不能像待办 4 那样"搭车"：它走的是**全局任务队列**，任务可能被任一 worker 取走，而"响应缓冲"只能由**属主 worker** free ⇒ 只能按 worker 单独建通道。

### 8.2 方案：每个 worker 一个"单生产者/单消费者（SPSC）无锁队列"

- **生产者 = 收发线程（只有 1 个）**，**消费者 = 该 worker（只有 1 个）** ⇒ 不是 MPSC，而是更简单的 **SPSC**；
- **侵入式链表**：待释放的响应块已经发完、内容作废 ⇒ **直接用它自己的前 8 字节当 `next` 指针** ⇒ **零额外内存、零 malloc**；
- **没有容量字段** ⇒ `push` 永远成功、永不阻塞 ⇒ **没有"满"，没有信号量，没有阻塞点**。

```c
typedef struct Free_Node { struct Free_Node* next; } Free_Node;

typedef struct {
    _Atomic(Free_Node*) head;   /* 生产者（收发线程）发布新节点 */
    Free_Node*          tail;   /* 消费者（该 worker）自己用，不需要原子 */
} Free_Q;

/* 初始化：head = tail = 哨兵节点（静态或 malloc 一个，标记为哨兵） */
void FreeQInit(Free_Q* q, Free_Node* sentinel);

/* 生产者（收发线程）：原来 WorkerQueuePush 阻塞的位置 */
void FreeQPush(Free_Q* q, void* block){
    Free_Node* n = (Free_Node*)block;
    n->next = NULL;
    Free_Node* prev = atomic_exchange_explicit(&q->head, n, memory_order_acq_rel);
    atomic_store_explicit(&prev->next, n, memory_order_release);   /* 先备好再挂链 */
}
/* 永远返回成功：没有“满”，也没有返回值需要检查 */

/* 消费者（属主 worker）：批量取，空返回 NULL */
void* FreeQPop(Free_Q* q){
    Free_Node* t = q->tail;
    Free_Node* n = atomic_load_explicit(&t->next, memory_order_acquire);
    if(n == NULL) return NULL;      /* 空 */
    q->tail = n;
    return t;                       /* 返回“上一个”节点；初始哨兵需跳过 */
}
```

```c
/* worker 侧：CleanMemoryQueue 改成批量还（每任务 + 空闲时都调） */
void* p; int n = 0;
while((p = FreeQPop(&profes->free_q)) != NULL && n++ < 256)
    MemoryPoolFree(profes->txt_pool, p);      /* 属主线程 free，池无锁 ✓ */
```

### 8.3 为什么"不限长"是安全的（容量依据 —— 你的推理，记在此）

> **释放包与响应块一一对应**：一个 `MemoryPoolAlloc` 恰好产生一个"待回收包"，所以

```
队列长度 ≤ 已分配未归还的块数 ≤ 池总容量 / 最小块（needSize + 4）
```

- 也就是说**它天然有界**，不会无限增长 ⇒ "无上限的无锁队列"可以放心用；
- 而实际长度 ≈ **在途响应数**（"已发完、还没回收"的响应），受 `pack_in_path ≤ 100/连接` × 并发连接数 约束；
  例：400 并发、每连接 1 个在途 ≈ **400 条 × 8B ≈ 3.2KB** ⇒ 完全可以忽略；
- **"有界"≠"健康"**：队列变长的代价不是内存，而是"这些块的 `hadAllocNum` 不归零 ⇒ 子池回收不了 ⇒ 池有效容量下降 ⇒ 上层 503 提前"。所以：
  - `CleanMemoryQueue` **每个任务结束都调**（不只空闲时）；
  - 批量 pop 要**限个数**（如 ≤256），别把任务处理饿着；
  - 探针里盯"未归还包计数"，压测时它应长期接近 0。

### 8.4 这条"1:1"能成立的前提：四个破坏点必须先堵

| 破坏点 | 位置 | 新池下的后果 |
|---|---|---|
| `tempPack` 单槽覆盖 | `Threads/ReceiverThread.c:48-56` | 被覆盖请求的副本**永不还** ⇒ 该子池永久不可回收（队列的"界"越来越小） |
| `FdClose` 早退 | `FdConnectOrClose.c:49-51` `if(fd_ob==NULL) return 1;` | 发送槽里残留的响应块不会被清 ⇒ 一批块漏还 |
| "丢弃响应"（若加超时降级） | 待实现 | 响应块 / 搭车指针都要一并 free，否则同样漏 |
| 重复 push / 重复 free | 调用方纪律 | 新池**不校验** ⇒ 计数减错 ⇒ 子池提前复位 ⇒ **两个在用请求共用内存**（比泄漏更难查） |

⇒ 这也是"先把漏堵上、再换池"的原因：**换池前漏 1 块只是漏 1KB，换池后漏 1 块 = 永久少一个子池。**

### 8.5 落地要点

1. **块必须 ≥ `sizeof(void*)`（8B）**（要用前 8 字节存 `next`）；响应块一般够，但要写注释/断言；
2. **入队后不能再碰块内容**（前 8B 已是链表指针）⇒ 只能在"发送彻底完成"后入队（现在 `MemoryQueuePushOperate` 的位置就是对的）；
3. **消费者批量 pop 且限个数**（≤256/次）；
4. **内存序不能省**：发布用 `release`、消费用 `acquire`；初始化放哨兵，第一次 pop 跳过它；
5. 单生产者单消费者 ⇒ **不需要 CAS 循环**（一个 `exchange` 足够），但要保证"只有收发线程 push、只有属主 worker pop"。

### 8.6 与"方案 A（`sem_trywait` + 本地暂存）"的对比

| | 方案 A：非阻塞 + 本地暂存链 | **无锁 SPSC 队列（本方案）** |
|---|---|---|
| 有"满"吗 | 有（暂存也有上限，要定"满了怎么办"） | **没有，永不失败** |
| 收发线程会阻塞吗 | 不会 | 不会 |
| 代码量 | 暂存链 + 重试点 + 上限背压 | ~15 行无锁队列 |
| 额外内存 | 暂存链（指针数组） | **0**（复用待释放块自己） |
| 依赖 | 无 | `stdatomic`（`IncludeStandard.h` 已 include ✓） |

### 8.7 收益

- **死锁的另一条边消失**（投递永不阻塞）；
- 池依然 100% 无锁（free 只在属主线程）；
- 少一个信号量、少一次"满"的判断、少一份额外内存。
